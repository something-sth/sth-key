# 自定义 Key 样式

这份文档是**自定义 Key**（配置里 `styleId = "custom_key"`）的设计依据：
为什么这么设计、契约是什么、下一步做什么。

改动这个子系统之前先读这里；契约变了就回来同步。

---

## 1. 需求（已确认）

样式从两种（Key / LIVE 2D）增加到三种，新增**自定义 Key**：
窗口里有什么，全部由用户在编辑器里摆放的**组件**决定。

- 新建后默认布局：**一个 Q 键 + 一个 `CPS: (cps)` 文本**
- 组件分两种：
  - **按键组件**：监听按键，按下变色 —— 这才是"按键显示"
  - **文本组件**：只显示文字 —— 可以当水印，也可以单独显示 CPS
- **编辑页独立**，不与 Key / LIVE 2D 共用
  - 外层只留通用项：名称、描述、预览、重置、删除
  - 中间**只有一个「自定义编辑」按钮**，点进去才是真正的编辑器（二级页面）
- 编辑器：
  - 顶部功能栏：撤回、恢复、**设置栏位置（下 / 左 / 右）**、保存
  - 组件条（一横排胶囊 + 增/删/重置），**固定在画布上方**
  - 只读图形区：**不接收触摸**，只用来"看"
  - 属性面板：选中哪个组件就调哪个，**位置可切换**（见 2.9）
- **不采用实时更新**：点保存才写入。理由有二 ——
  一是出错不好维护，二是下面已经有图形化预览了

> ⚠️ 需求原文里写的是"拖动、对齐吸附（红线）、间距吸附（绿线）"。
> 这三样**都没做**：拖动在实现后被移除（难排查，见 2.10），
> 吸附中间试过一版"按钮式对齐"，后来按需求也删掉了（见 2.10 末尾）。
> 位置目前只能靠 X / Y 滑块 + 「居中」。

## 2. 已定的决策

| 事项 | 结论 |
|---|---|
| 样式 id | `custom_key`（snake_case，与 `keystrokes` / `keyboard_cat` 一致；不用带空格的写法） |
| 默认 Q 键绑什么 | 已有的 evdev 键码体系：`keyCode 16`（Q），与 Key 样式的键位映射同一套 |
| 原 Key 样式那些字段 | **自定义 Key 完全不用**。Shift / 鼠标键用组件表达；CPS 只**复用文本模板逻辑** |
| CPS 占位符 | 复用 Key 样式那一套：`(cps)` 与 `(cps2)`，不另造规则 |
| **CPS 怎么开关** | **没有开关**：文字里有占位符就显示，删掉占位符就是关掉 —— 见 2.8 |
| **CPS 统计哪些键** | **多选**（与键位映射同一个交互）。按键组件用它**自己监听的键**（不用选）；文本组件用 `cpsKeyCodes`（**只在文字含占位符时才出现**）—— 见 2.1 |
| 定位方式 | **X / Y 滑块 + 居中**，画布不接收触摸；**没有吸附对齐** —— 见 2.10 |
| 文字偏移的语义 | **只挪文字**，不影响组件边框 —— 吸附对齐永远按边框算 |
| 推进方式 | 分两步：先地基（数据/存储/渲染/默认布局/样式注册），再做编辑器 |

### 2.1 CPS 统计哪些键：按键组件**跟着自己的映射**，文本组件才要选

原先文本组件只能选"左键 / 右键"（`cpsSlot`），那是照搬 Key 样式的思路。
但自定义 Key 的意义就是什么都能摆 —— 想给 Q 键显示"每秒按了多少次"完全合理。

所以取值来源是**输入键码列表**，逐个翻译成键位后再读计数：

```
组件指向的输入键码（见下，可多个）
        ↓ 翻译（键位映射反查：CpsCounter.slotOf → KeyLayout.codeToSlotMap）
键位 id 集合（**先去重**，见下）
        ↓ 读计数并**相加**
数值 → 替换文字里的占位符
```

**"组件指向哪些键"由 `CustomLayout.cpsKeyCodesOf` 回答**，两种组件不同：

| 组件 | CPS 来源 | 用户要不要选 |
|---|---|---|
| **按键组件** | 它自己的 `inputKeyCodes` | **不用**。它已经映射好了 |
| **文本组件** | 它自己的 `cpsKeyCodes`（默认鼠标左键） | 要，但**只在文字含占位符时才显示这个选项** |

按键组件刻意**没有**单独的 CPS 键字段：加了它就等于开了第二个真源，
用户可以改一个忘一个，出现"按键亮的是 Q、CPS 数的是左键"这种自相矛盾的状态。
这正是需求原话"Key 组件不需要额外的 cps 统计按键选择，可以直接采用这个组件映射的按键"。

#### 两处都是**多选**（与键位映射同一个交互）

键位映射那边一个位置可以绑多个物理键（左右 Shift 共享一个计数）。
自定义 Key 这边照抄同一个交互：`AssistChip` 列出已选键 + 笔形按钮打开多选对话框
（`MultiKeyPickerDialog`，**两个界面共用一个实现**）。

多选不是锦上添花而是必需的：左右 Shift 是两个不同的键码，
只绑一个的话另一边按下去不亮。

#### ⚠️ 求和前必须按键位**去重**

左右 Shift 是两个不同的键码，但在键位映射里是**同一个位置**、共享一个计数。
用户把两个都选上时，CPS 应该是那个计数的值，而不是它的两倍 ——

```
cpsKeyCodesOf(c) = [42, 54]
        ↓ slotIdOf
["SHIFT", "SHIFT"]  ← 不去重就在这里错
        ↓ distinct()
["SHIFT"]
        ↓ 求和
cpsBySlot["SHIFT"] = 7   ✓（不是 14）
```

这个错**只在多选时出现**，而且表现是"CPS 偶尔翻倍"，
很难联想到是求和这一步 —— 有测试钉着（`多个键映射到同一个位置时只算一次`）。

推论：

- `cpsKeyCodes = [BTN_LEFT]` 就等价于原来的"左键"；
- 一个键都不选 → CPS 恒为 0（这不是"关闭"，关闭靠删占位符）；
- 翻译不出位置的键码**不参与求和**（那种情况调试面板会标出来）。

⚠️ **跟着映射走的代价**：组件指向的那些键必须在**当前配置的键位映射**里存在，
否则翻译不出槽位。默认配置的映射里只有 WASD / SPACE / SHIFT / LMB / RMB，
所以给一个绑 `keyCode 16`(Q) 的组件显示 CPS，得先在键位映射里加上 Q。
调试页的 CPS 自诊断面板会把模板 → 键码 → 槽位 → 数值这四层都列出来。

### 2.2 文本组件也有键帽

第一版把文本组件的底色默认做成全透明，结果它在屏幕上是一串"裸字"，
看起来像缺了键帽。这是错的：**能被拖动、能被对齐、能被描边的就是一个元件**，
外观上不该和按键组件是两种东西。

现在两者共用同一套默认主题（黑底白字、70% 不透明）。
不想要背景的用户把不透明度拉到 0 即可 —— 但默认值应该是"看起来像个正常元件"。

### 2.3 CPS 计数不再限制槽位（否则 CPS 永远是 0）

`CpsCounter.recordClick` 里原本写死 `if (slotId != LMB && slotId != RMB) return`，
那是"CPS 只能显示鼠标点击"时代的假设。放开这个限制（任何槽位都计数）之后，
CPS 才可能绑到键盘键上。

配套两件事：

1. 调试页的**模拟按键也会计数**（走同一个 `recordCpsClick`），
   否则调试页按得再欢 CPS 也是 0，看起来像功能坏了；
2. 刷新循环的判据见 2.4 —— 不是看 Key 样式的那个开关。

### 2.4 CPS 必须**按配置隔离**，且刷新判据不能只看 Key 样式的字段

这两个都是真机上暴露出来的，一起说。

**（a）"数字翻倍"的坑。**
计数是按**键位 id** 记的，而"这个 id 属于哪份配置"是配置自己的事：
三份配置都可能有一条 `LMB` 映射。曾经为了"多窗口下谁都能显示 CPS"，
让一次点击**遍历所有配置各记一次** —— 结果三份配置就把一次点击记成三次，
用户看到 CPS 直接翻三倍。

现在每个配置 id 一个计数器：

```
recordCpsClick(context, code)
  → 取「开着悬浮窗的配置」（一份都没开时退回第一份）
  → 逐个用**该配置自己的**键位映射查槽位
  → CaptureSession.recordCpsClick(configId, slotId)
显示时 → CaptureSession.cpsSnapshotOf(config.id)
```

⚠️ 顺带维护 `CaptureSession.cps`（全局计数器）：调试页的面板还在读它。
**只写一处就会出现"某一边永远不动"**。

**（b）刷新循环起不来。**
原来 CPS 的刷新循环挂在 `KeyStrokesConfig.mouseCpsEnabled` 上 ——
那是 Key 样式的字段，自定义 Key 配置里它永远是 false，
于是 `cps` 一直是个空表，数字**停在初始值不动**（看起来像"没有数字"）。

现在判据是"这份配置到底用不用 CPS"，由样式自己回答：

| 样式 | 判据 |
|---|---|
| Key | `mouseCpsEnabled`（它还有"显示哪个位置"的额外逻辑） |
| 自定义 Key | `CustomLayout.usesCps(components)` —— 有没有组件真的绑了 CPS |

### 2.5 "CPS 行"与"组件文字"是同一段文字，不能画两遍

真机上出现过这一幕：诊断面板算出 `显示 "CPS: 5"`（数据全对），
但悬浮窗上只看到一团 `CPS:` 相关的东西、没有数字。

原因是渲染层把文本组件画成了**两行**：

| 行 | 内容 | 字号 |
|---|---|---|
| `primary` | 组件自己的文字，也就是**模板** `CPS: (cps)` | 正常 |
| `cpsLine` | 替换后的结果 `CPS: 5` | **小一号** |

文本组件的文字**本身就是 CPS 模板**，不存在"键名 + CPS"这种两行结构 ——
那是按键组件的形态。画两行不但挤，还会让人以为"数字没出来"。

现在按组件类型决定显示哪几行：

| 组件 | 显示 |
|---|---|
| 文本组件 | **只有替换后的那一行**（`CPS: 5`） |
| 按键组件 | 键面文字 + CPS 两行（与 Key 样式模式 3 一致，CPS 小一号） |

### 2.6 模板**只有一个真源**

早先绑定对象里存了一份 `text`，组件自己也有一份文字 —— 同一个东西两个真源。
后果很隐蔽：**诊断面板按那份算，渲染按组件的文字画**，
两边可以不一致，而且从任何一边看都"逻辑正确"。

现在**没有绑定对象了**（见 2.8），模板只有一个来源：

- 文本组件 → 模板是它的 `text`
- 按键组件 → 模板是它的 `label`

CPS 行就是"把组件那段文字替换一遍"，如此而已。

> 通用教训（与 `docs/live2d.md` 里"重置参数两份实现"是同一条）：
> **任何"必须保持一致"的东西，全项目只能有一份**。
> 加字段时先问：这个值和别的字段是不是在描述同一件事？

### 2.7 诊断要放进应用里，不能只写日志

排查 CPS 这类问题需要**三层**信息：组件里存了什么绑定、绑定翻译成了哪个槽位、
那个槽位这一刻的数值是多少。光看悬浮窗只能看到最后一层的结果（一个空串），
分不清是"没绑上""翻译不出来"还是"数值确实是 0"。

教训：**日志不是给用户看的界面**。日志会被级别/关键字过滤挡掉、
会被后续日志挤出缓冲区（上限 2000 条）、还要求用户知道去哪儿翻。
所以调试页里直接加了一块**「CPS 自诊断」面板**
（`cpsDiagnosticReport`，每秒刷新一次），把三层并排摆出来：

```
配置「布吉岛样式」(b920fbe8)
  CPS 计数：{LMB=3}
  键位映射：17→W, 30→A, 272→LMB, 273→RMB
  组件 text_cps：模板 "CPS: (cps)" → 键码 272 → 槽位 LMB → 数值 3 → 显示 "CPS: 3"
```

一眼就能看出是哪种病因。三种"没有 CPS"的原因各自可辨：
**没写占位符**（面板里直接说"没有一个写了 `(cps)`"）、
**键没映射**（槽位那一段写"翻译不出来"）、**确实还没点过**（数值 0）。

日志那条（`CPS 诊断：…`）保留，但只是留个历史。

同类问题以后照这个标准办：**能用面板说清的，就不要让用户去读日志**。

### 2.8 CPS **没有开关**，占位符就是开关

早先每个组件有一个 `cps` 绑定对象加一个"显示 CPS"开关，打开后才渲染第二行。
三个问题：

1. **开关是多余的** —— "要不要 CPS"本来就是"文字里写不写占位符"这件事，
   再给一个开关就是同一个决定有两个入口，两者还可能互相矛盾
   （开关开着但文字里没占位符 → 用户看到一片空白，不知道哪里不对）；
2. **"显示哪一项"选错了也是一片空白**（同上）；
3. **两种组件的规则还不同**，渲染与诊断代码到处 `when`。

现在与 Key 样式**完全一致**：

> **文字里有 `(cps)` 或 `(cps2)` 就显示 CPS，没有就不显示。**

```
LMB(cps2)  →  LMB      （为 0）
           →  LMB 5    （不为 0）
CPS: (cps) →  CPS: 0 / CPS: 5
水印        →  水印      （没有占位符 → 没有 CPS）
```

于是 `CpsBinding` 这个类**整个删掉了**，"关掉 CPS"就是删掉占位符。
判据只有一处：`CustomLayout.hasCpsPlaceholder()`，
渲染、刷新循环（`usesCps`）、调试面板都用它 ——
三处判据不同的话就会出现"定时器在跑但屏幕上没东西"。

> ⚠️ 这一改动顺带修掉一个**真 bug**：早先渲染层是"主文字画一遍、CPS 行再画一遍"，
> 而主文字用的是**没替换过的模板**。所以文本组件的 `CPS: (cps)` 在屏幕上
> 是**两行**：`CPS: (cps)` 和 `CPS: 5`。代码注释里甚至写着"只渲染替换后的那一行"，
> 实际没做到。现在只有`CustomLayout.displayText()` 一条路径，不可能再分叉。

### 2.9 属性面板可换边（下 / 左 / 右）

属性面板是按"手机竖屏、面板在下方"设计的：一列滑块，宽度吃满、高度占大半屏。
换到平板上就完全不对了 —— 横屏时上下空间很矮，面板被压成一两条缝，
而左右两侧大片空白没人用。所以位置交给用户选（`EditorPanelSide`）。

| 选项 | 行为 |
|---|---|
| 下 | 手机竖屏的默认 |
| 左 | 平板横屏推荐（宽度固定 330dp） |
| 右 | 与左对称（平板左右无实质差别，保留给习惯右手的人） |

#### 没有"上"

面板在上时画布就跑到下面，而软键盘是从底部弹起来的 ——
改文字时画布会被顶掉一半，被编辑的组件恰好在画布里，边打字边看不到效果。
下/左/右三种都与键盘错开。

#### ⚠️ 也没有「自动」这个**按钮**（这里换过一次做法）

早先界面是四个按钮（下/左/右/**自动**），"自动"自己占一格。
但它不是一个**位置**，而是"位置从哪来" —— 混在一起之后，
选了自动的用户还是不知道面板现在在哪一边，而这两者在屏幕上差别很大。

现在改成：偏好的初值是 `AUTO`，界面把它解析成具体的一边
（平板→左、手机→下）；**三个按钮里被自动选中的那个带 `-自动` 后缀**
（例如 `左-自动`）。于是"在哪一边"和"是不是自动定的"一眼都看得到。
用户一点按钮就变成明确的位置并写回偏好（`editorPanelSideChosen` 置上）——
否则他手动切到下方、下次打开又被自动改回左边，看起来就像设置没记住。

判定"是不是平板"用 `smallestScreenWidthDp >= 600`（官方的 sw600dp 口径）：
它描述**设备形态**，转屏时不变，所以不会横竖屏一切换就换边。

#### 组件条固定在顶部

不跟着面板走：它是"选哪个组件"的入口，而面板是"改这个组件"的地方。
钉在画布上方，切换面板位置时选组件的动线完全不变。

#### 面板内部是**五个可折叠组**

```
内容        文字 / 监听的键（多选）/ CPS 说明或「CPS 统计的键」（多选）
位置与尺寸  居中 / X / Y / 宽 / 高
外观        未按下（透明度·颜色·缩放·偏移·字体）+ 按下时（透明度·颜色）
描边与圆角  描边开关·粗细·颜色 / 圆角开关·程度
按下动画    模式 / 时长
```

前两组默认展开。早先接近 20 个控件排成一列，一屏看不完，
而且大部分当前用不到（文本组件那一半是灰的、没开描边时"描边粗细"是多余的）。

> ⚠️ **"按下时"在「外观」组里，不是单独一组**（这里也换过一次分组）。
> 未按下与按下是同一件事的两个状态，调的时候几乎总是来回对比着改 ——
> 分成两个折叠组的话，每次对比都要展开-收起一次，纯属白费操作。
> 现在它们是同一屏里的上下两段，中间只隔一个小标题（`SubLabel`）。
> 文本组件没有"按下"这个状态，所以它看不到那两个小标题。

展开状态**按组件 id 重置** —— 不重置的话，从按键组件切到文本组件时
"按下动画"那一组消失，面板会看起来空了一截。

### 2.10 定位用 X / Y 滑块，画布**不接收触摸**

第一版让用户在画布上拖动组件。那套东西引入了 `awaitEachGesture` 手势、
工作区缩放、命中坐标换算、`pointerInput` key 与内容变化的相互影响 ——
复杂度和收益完全不成比例，而且出问题时（看起来"整个界面都是死的"）
极难定位到底是手势、坐标还是状态传播。

现在：**画布只负责看，属性面板负责改**，定位走 X / Y 滑块 + 「居中」。
这个页面**一行触摸处理都不需要**，所有编辑都走同一类控件（滑块），
坏就一起坏、好就一起好，排查面小得多。代价是失去"直接拖"的直觉，换来的是可靠。

⚠️ 连"点画布上的组件来选中"也去掉了：那需要把点击坐标换算回基础坐标，
而画布的缩放倍率是量出来的 —— 换算错一点就会出现"点 A 选中 B"。
选中统一走**上方那一条组件条**，那是一排成熟的控件，不需要任何坐标换算。

#### 吸附对齐：试过一版，按需求删掉了

需求原文是"拖动时出现红线对齐、间距等于设定值时出现绿线"。
拖动被移除之后那套东西没有立足点了，于是中间做过一版**按钮式对齐**：
点一下把选中的组件贴到最近的参考线（其它组件的边框、画布三线、
间隔等于设定值的位置），X/Y 各自独立判定，纯函数 + 13 条测试。

后来按需求**整个去掉了**（"没啥卵用"）—— 判断是对的：
滑块本身就能精确到 1 个单位，而"对齐"在只有几个组件时收益很小，
却要多占一个按钮、多一套设置（吸附开关 + 间距）。一并删掉的还有：

- `domain/custom/CustomSnap.kt` 与它的 13 条测试；
- `CustomLayoutSettings` 里的 `snapEnabled` / `snapGapDp` 两个字段
  （留着就是"改了会存进配置但看不出效果"的骗人设置）；
- 草稿层的 `setSnapEnabled` / `begin-update-endSnapGapDrag` 那一对 API；
- 界面上的「吸附对齐」按钮、吸附开关、键吸附间距滑块。

真要恢复：逻辑在 git 历史与本文档的这一节里写清了，
字段加回去即可 —— 编解码是宽容的，老配置缺字段只会用默认值。

### 2.12 复制组件：id 必须换掉，位置必须偏一点

组件条上加了「复制」，与「添加 / 删除 / 重置」并列。它的实现是
`domain/custom/ComponentFactory.kt` 里的 `duplicateComponent`，
有两个不能省的细节 —— **两个失败方式都不会报错，只会看起来很奇怪**：

**1. id 必须换掉。** `CustomLayoutDraft.replace` 是**按 id** 找组件替换的，
两个组件同 id 会变成"改一个另一个也跟着变"。用户会以为"复制出来的东西是联动的"，
而实际是数据坏了 —— 这是最难看懂的一类 bug。

⚠️ 而**时间戳不足以保证唯一**：复制是"点一下就有结果"的操作，
连点两下就可能落在同一毫秒里。所以 `newComponentId` 拿现有 id 集合去重，
撞了就往后顺延。多花一次遍历，换掉一整类怪问题。

**2. 位置必须偏一点。** 副本与原件逐像素重合的话，用户点了复制什么也看不见，
会以为按钮坏了。偏移 24 个基础单位。

⚠️ 但**偏移会被夹取吃掉**：原件贴住右边界时 `+24` 又被夹回原位，
副本还是压在原件上。所以夹取之后要察觉"位置一点没动"，改往左上偏 ——
这就是 `duplicateComponent` 里那个 `if` 的全部理由。

> 用"位置没变"而不是"原件太靠边"来判断：后者要自己重算一遍边界，
> 而边界规则（下界依赖尺寸）已经在 `clampedToCanvas` 里了，
> 在那边再算一遍就是第二个真源。

副本与原件**完全一样**（文字、绑定的键、全部外观）：不做"自动加个 2"之类的改名 ——
那是编辑器的自作聪明，用户想在副本上写什么他自己会改，
而自动加的后缀他首先要删掉。

### 2.13 删除组件要确认

与「恢复默认布局」同一个待遇：两者都是**一键就毁掉一段成果**的操作。
弹窗里写清删的是哪一个（类型 + 内容摘要），否则用户很容易在
"选中的其实不是自己以为的那个"时点下去。

删完把选中项挪到剩下的第一个 —— 不挪的话 `selectedId` 会指向一个
已经不存在的组件，属性面板变成"没有选中组件"，而用户刚删完正想接着改下一个。

### 2.14 属性面板的文字输入框必须有**本地状态**

上一版的输入框写的是 `value = component.primaryText()` ——
值**直接来自草稿**。后果是每敲一个字符都要走"草稿 → 重组 → 新值"这一圈，
而且**每个字符都 commit 一步撤回**。用户看到的是"打不进字、退格删的不是刚打的字"。

现在按 `HexColorRow` 的做法：本地 `remember` 一份文本，
外部值变化时用 `LaunchedEffect` 同步回来。输入过程只写本地状态，
同时照实写进草稿（画布保持实时），但 UI 不再依赖那一圈往返。

> 规矩：**输入框的值不要直接绑到会被自己改写的状态上。**
> 本地状态 + 单向同步是这类"输入体验异常"的标准解法。

## 3. 数据模型

### 为什么 CPS 是"复用文本逻辑"而不是重做一套

Key 样式已经有一套很明确的约定，用户已经熟悉：

| 写法 | 数值为 3 | 数值为 0 |
|---|---|---|
| `CPS: (cps)` | `CPS: 3` | `CPS: 0` |
| `CPS: (cps2)` | `CPS: 3` | `CPS:`（只去掉数字那段） |
| `(cps2)` | `3` | 整段隐藏 |

自定义 Key 的文本组件**逐个字符照搬**这套规则。两套替换逻辑一旦分叉，
"在这里学会的写法换个样式就不成立"，是最容易招人烦的那类不一致。

## 3. 数据模型

```
KeyStrokesConfig
├── …（Key 样式那一整套，自定义 Key 一个都不用）
└── custom: CustomLayoutSettings        ← 新开的一块，与 live2d 对称
    └── components: List<CustomComponent>   渲染顺序 = 列表顺序（后画的在上）
```

> 早先这里还有 `snapEnabled` / `snapGapDp` 两个吸附设置字段，已随吸附一起删掉
> （见 2.10 末尾）。编解码是宽容的，老配置里多出这两个键不会有任何影响。

组件是两个 `data class` 加一个 `sealed interface`：

| | 按键组件 | 文本组件 |
|---|---|---|
| 监听按键 | ✅ `inputKeyCodes`（**多选**） | — |
| 按下态（颜色/透明度） | ✅ | — |
| 按下动画 | ✅ | — |
| 键面文字 | `label`（如 `Q` / `LMB(cps2)`） | — |
| 主体文字 | — | `text`（可含 CPS 占位符） |
| **CPS 统计哪些键** | 就是它监听的键，**不用另选** | `cpsKeyCodes`（**多选**，默认左键） |
| 文字缩放 / 偏移 | ✅ | ✅ |
| 颜色 / 透明度 / 描边 / 圆角 / 字体 | ✅ 共用 `ComponentStyle` | ✅ 同左 |

**主题（`ComponentStyle`）两者共用**：以后加"图片组件"时，
颜色/描边/圆角那部分不用再抄一遍。

**CPS 没有绑定对象了**（`CpsBinding` 已删）：要不要显示 CPS 由
文字里有没有占位符决定，"统计哪些键"两种组件各有各的天然答案 —— 见 2.1 与 2.8。

**颜色与透明度分开存**（与 `ColorSet` / `Opacity` 同一个理由）：
颜色只存 24 位 RGB，透明度单独存百分比 —— 各自只有一个真源，
不会出现"改颜色把透明度也改了"。

### 坐标系与窗口尺寸

所有坐标都是**基础坐标**（与 `KeyLayout` 的 BASE_WIDTH 体系一致）。
组件**不感知整体缩放**：`scalePercent` 统一乘在上面。

```
定位区 = 固定 600 × 600（BASE_CANVAS）      X/Y 滑块的范围是 [−尺寸, 600]
悬浮窗 = 所有组件边框的**最小外接矩形**      随内容变化，贴着内容
窗口尺寸 = 包围盒 × 整体缩放 + 内边距×2
```

#### 定位区与窗口是**两件事**（这条最容易混）

早先它们是同一个概念（画布 = 窗口 = 内容包围盒），于是有两个真实后果：

1. **位置滑块的取值范围没有确定的上界** —— 画布尺寸取决于组件位置，
   而滑块上界又要反过来参考画布。自我递归，只能靠瞎猜一个数；
2. 把组件往外挪一点，**整个窗口跟着长大**。

后来改成"两边都固定 600×600"，递归问题解决了，但**窗口占地方非常大** ——
默认布局只占一角，屏幕上却是一整块 600×600 的空白。

现在拆成两个概念，各管各的：

| | 定位区 | 悬浮窗 |
|---|---|---|
| 大小 | 固定 600×600 | 内容包围盒 |
| 作用 | X/Y 滑块的取值范围 | 屏幕上实际占多大 |
| 会变吗 | 永远不变 | 跟着内容变 |

**滑块范围因此与窗口尺寸解耦**，不再自我递归；窗口则贴着内容，不占多余地方。

#### 窗口范围的算法：`CustomLayout.bounds`

```kotlin
Bounds(offsetX, offsetY, width, height, visible)
      └─ 包围盒左上角         └─ 宽高      └─ 有没有组件
```

三处细节都有测试钉着（`CustomLayoutBoundsTest`）：

- **宽度用右边界**（`maxOf { x + width }`），不是左边界的最大值 ——
  用后者会把最右边那个组件裁掉一半；
- **偏移可以负**：组件允许贴到定位区外沿，坐标就是负的；
- **没有组件时给 1×1**：尺寸为 0 的窗口在 `WindowManager` 里是无效参数，
  直接崩。1×1 得到的是一个看不见的点 —— 反正也没内容可画。
  编辑器里会明确提示「悬浮窗 不会显示（没有组件）」。

#### ⚠️ 内容必须按包围盒**平移**，否则跑到窗口外

组件坐标的原点是**定位区的左上角**，而窗口只覆盖包围盒 ——
两者不是同一个原点。放在 (300, 400) 的组件，如果不平移就直接画在
窗口坐标系里，会落在窗口外面，**在屏幕上彻底看不见**。

所以 `CustomKeyCanvas` 多了一对 `contentOffsetX/Y`：

| 调用方 | 偏移 | 尺寸 |
|---|---|---|
| 悬浮窗 | 包围盒左上角 | 包围盒宽高 |
| 编辑器画布 | 0 | **定位区**（画的就是整个定位区） |
| 配置预览 | 包围盒左上角 | 包围盒宽高 |

窗口尺寸（`OverlayStyleRegistry.baseSizeOf`）与内容平移（`OverlayContent`）
各自消费一次 `bounds` —— 同一个纯函数，必然同一个结果。
**不允许任何一处自己算**，否则内容会偏。

#### 编辑器里两个框都画

```
┌ 虚线外框 = 定位区 600×600（X/Y 滑块的范围）┐
│   ┌ 实线内框 = 悬浮窗范围 ────┐            │
│   │  组件                    │            │
│   └─────────────────────────┘            │
└──────────────────────────────────────────┘
```

画布**画定位区而不是窗口**，是刻意的：窗口会随组件移动而变化，
如果画布就画窗口，那么**挪任何一个组件，整个画布都会跟着移、跟着缩放**，
拖滑块时视觉参考一直在动，根本没法判断"我现在挪到哪了"。
定位区固定，参考系才是稳的。

属性面板的「位置与尺寸」把两个数都写出来（画布 600×600 / 悬浮窗 175×120），
否则用户看到画布上大片空白会以为窗口也那么大。

#### ⚠️ 坐标下界跟着尺寸变 → "改尺寸"也必须夹坐标

下界是 `-尺寸`，**它随尺寸变**。一个贴住左边界的组件（x = −200、宽 200）
被缩到宽 50 之后，合法下界变成 −50，而 x 还停在 −200。
这时 X 滑块读到的值已超出自己的范围、会被夹到 −50 显示，
用户一碰滑块组件就**凭空跳 150**。

所以不变量是"**任何时刻**坐标都在范围内"，而不是"只有直接改坐标时才检查"：
`resizedTo()` 内部会 `clampedToCanvas()`。有测试钉着。

> **组件条的四个按钮**按"造东西 / 删东西"分成两组：
> `+` 添加 · 复制 ┃ 删除 · 重置。
> 手指记住的是"前两个是造、后两个是删"，比随便排要少点错。
> 复制与删除都需要先选中一个组件，没选中时是灰的。

> **组件条固定在画布上方**，不跟着属性面板换边 ——
> 它是"选哪个组件"的入口，钉在那里，切换面板位置时的动线完全不变。
>
> 顶栏第二行的三个按钮里，**被自动选中的那个带 `-自动` 后缀**（如 `左-自动`）：
> 一眼同时看出"面板在左边"和"这是自动定的、不是我选的"。

#### ⚠️ 定位用 X / Y 滑块，画布**没有**任何手势（这里换过一次方案）

第一版让用户在画布上拖动组件。那套东西引入了 `awaitEachGesture` 手势、
工作区缩放、命中坐标换算、`pointerInput` key 与内容变化的相互影响 ——
复杂度和收益完全不成比例，而且出问题时（看起来"整个界面都是死的"）
极难定位到底是手势、坐标还是状态传播。

现在：**画布只负责"看"，属性面板负责"改"**，定位走 X / Y 滑块。
于是这个页面**一行触摸处理都不需要**，所有编辑都走同一类控件（滑块），
坏就一起坏、好就一起好，排查面小得多。

代价是失去"直接拖"的直觉，换来的是**可靠** —— 摆一个悬浮窗布局时这是划算的。

顺带去掉的还有"顶部功能栏收起/展开"：功能栏只有两行，
收起来省的那点空间不值得多一个状态。

> **吸附对齐也删掉了**（先是拖动没了、后来按钮式那版也按需求去掉）：
> 按钮、开关、间距滑块、`CustomSnap.kt` 与它的 13 条测试、
> `snapEnabled` / `snapGapDp` 两个字段，全部移除。见 2.10 末尾。

**还没做**（都明确推迟，不是遗漏）：

1. 画布平移/缩放、框选多选、图层顺序的显式调整
2. 真机验证（本机没有连设备，目前只能靠编译 + 单元测试保证）

### 写这一步时踩到的六个坑

**1. 滑块拖动的几十次中间状态会把撤回栈塞满。**
所以 API 设计成成对的"开步 / 中途改 / 收尾"（`mutateOnce` / `assign` / `finishStep`）。
⚠️ 第一版只暴露了一个 `setSnapGap(gap) = assign { … }` —— 那是**半成品**：
既不开步也不收尾，结果是**历史一次都没推进过，撤回永远是灰的**，
而且它看起来完全正常，调用方不会怀疑。

> 规矩：**半成品 API 不对外**。对外只给 `beginXxxDrag / updateXxxDrag / endXxxDrag`
> 这一整套 —— 只要用到其中一个，另外两个必然会被调用（拖动一定有开始和结束）。

**2. `mutateOnce` 必须真的把起点压进历史。**
第一版只设了个 `stepOpen` 标记，以为"起点已经在栈里" ——
但写入是**就地替换** `history[cursor]`，于是"拖动前"那份状态被就地改掉了，
撤回回不到原位。测试直接抓到了（`expected 10.0 but was 100.0`）。

**3. 裁剪历史时不能把刚压进去的撤回锚点裁掉。**
`trimHistory` 无条件 remove 的话，`cursor` 会归 0、撤回直接失效，
而且**只在连续操作很久之后才出现**，用户看到的是"摆了半天，撤回按钮突然灰了"。
现在裁剪条件带 `cursor > 1`，并有测试钉住。

**4. 滑块外面套手势处理器会让它彻底拖不动。**
为了给撤回栈标记"操作开始"，我在滑块外套了一个 `pointerInput`，
一按下就调 `onBegin()`。结果那个处理器与 Slider 自己的手势竞争，
`awaitFirstDown` 拿到事件后，后续移动不再可靠地送给 Slider ——
**所有滑块都拖不动，连开关也是**。

改成用 `onValueChange` 的首次回调去重标记开始、`onValueChangeFinished` 收尾，
Slider 的手势完全不插手。

> 规矩：**不要为了"顺便做点别的事"而包住一个交互控件的手势**。
> 用它的回调，别抢它的事件。

**5. 最严重的一个：草稿不是 Compose 状态 + 输入框没有本地状态。**

现象很有迷惑性：开关点了**只出现聚焦效果、值不变**；滑块拖不动；
输入框打不进字（打进去立刻被旧值覆盖）；而"组件列表切换"和"保存"却正常。

两个**独立**的根因叠在一起：

- `CustomLayoutDraft` 的 `history` 是普通 `mutableListOf`、`current` 是普通 `val`
  —— 改草稿**不触发任何重组**。我当时另加了一个 `revision` 计数器 + 满地
  `refresh()`，以为读过它的地方会重组，但 `revision` 只能让**读过它**的那个作用域
  失效，属性面板与顶栏压根没读。
  修法：整份草稿装进一个 `mutableStateOf`，任何 `draft.current` 的读取
  **自动**订阅重组，调用方一个 `refresh()` 都不需要。

- 文本输入框写的是 `value = component.primaryText()`，**值直接来自草稿** ——
  每敲一个字符都要走"草稿 → 重组 → 新值"这一圈，而且**每个字符 commit 一步撤回**，
  退格时看到的就是"删掉的不是我刚打的字"。
  修法：按 `HexColorRow` 的做法，本地 `remember` 一份文本，
  外部值变化时用 `LaunchedEffect` 同步回来。

> 规矩一：**不要手写刷新令牌。** 状态放在 Compose 状态里，让依赖关系自动成立。
> 手写令牌漏一处就是一个"点了没反应"的 bug，而且它看起来完全正常。
>
> 规矩二：**输入框的值不要直接绑到会被自己改写的状态上。**
> 本地状态 + 单向同步（`remember` + `LaunchedEffect`）是这类"输入体验异常"的标准解法。
>
> 排查提示：当"一部分控件能用、另一部分不能用"时，先看
> **能用的那些是不是恰好读了真正的状态**。这个规律比逐个控件调试快得多。

**6. `object` 里的扩展函数是"成员扩展"，导入不了。**

把 `resizedTo` / `centeredOnCanvas` 写进 `object CustomLayout` 之后，
`import com.something.sthkey.domain.custom.resizedTo` 直接报
`Unresolved reference`，`component.resizedTo(...)` 也调不了 ——
成员扩展函数需要**两层接收者**（`with(CustomLayout) { component.resizedTo(...) }`）。

修法：**纯计算的规则留在 object，改字段的扩展放文件级**（`ComponentExtensions.kt`）。
这个坑踩过两次（第一次是把 `movedTo` 放进去，第二次是 `resizedTo`），
已经在两个文件里都写了注释，别再搬回去。

### 一条工程教训：不要用 PowerShell / 正则改源文件

我用 `Set-Content`（或 `-replace`）改 Kotlin 文件，两次都出事：
一次把字符串字面量改坏，一次把整个文件的中文变成乱码（UTF-8 → ANSI 往返），
而且部分行被合并、文件甚至不再是合法 UTF-8。
**改代码只用编辑工具（保留编码）；要批量改名用 IDE 的重构。**
如果确实要在命令行处理，必须显式指定读写编码，且**不要**用文本管道重写整个文件。

### 怎么确认装的是哪一次构建

`versionName` 开发期间不动（当前 2.3.0），所以界面上原本看不出新旧包。
现在 `app/build.gradle.kts` 把**构建时刻**写进 `BuildConfig.BUILD_TAG`
（格式 `MMdd-HHmmss`），在「关于」页显示成 `构建 0926-185702`。
它不是版本号，**不要拿它做任何判断**（公告、配置包都不该看它）。

精确到**秒**而不是分钟：改一行代码重建只花十几秒，
只到分钟的话前后两次构建显示同一个标记，"换了包没有"反而判断不了。

⚠️ 它只在**第一次**配置项目时确定：Gradle 的配置缓存命中时项目不会重新配置，
所以连续构建拿到的是同一个值。这是"编译期常量"的固有性质，不是 bug。约定是：

> **打包发布前 `./gradlew clean` 一次**，标记就会刷新到那一刻。

没有搞"每次构建自动刷新"：那需要额外的任务 + 输出文件 +
让 `GenerateBuildConfig` 依赖它，为了一个诊断用的标记去动构建流水线不划算。

### 真机反馈修掉的四个问题

**1. `scale` 的语义是"基础单位 → dp"，不是"→ 像素"。**

`CustomKeyCanvas(scale)` 内部写的是 `(值 * scale).dp`，也就是说它要的是
**dp 倍率**（悬浮窗那边传的是 `pxToDpFactor(density) × 整体缩放`，同一个东西）。

第一版我把它当成像素倍率用：给工作区 Box 设了 `size(workWidth * scale)`（这是 dp），
却把同一个 `scale` 当成像素来理解，于是**组件少缩了一次**、
而虚线画布框是按 dp 算的、尺寸是对的。
用户看到的就是"虚线框很小、按键贴图很大而且对不上"。

现在编辑器**全程按 dp 走**，与悬浮窗同构：

```
画布显示边长 = min(可用 dp 宽 / 600, 可用 dp 高 / 600, 1) × 600   （dp）
渲染倍率     = 画布显示边长 / 600                                 （dp 倍率）
组件            = CustomKeyCanvas(scale)          （它自己转 dp）
选中框 / 网格   = 值 × 渲染倍率 × density          （DrawScope 里是像素）
```

> 排查方法值得记一下：**用图像工具量截图**。
> 目测只能说"框很小"，量出来是"虚线框 215px（= 210 基础单位 × scale≈1.02，正确）、
> 键帽 230px（应为 80 × 1.02 ≈ 82px，差了密度 2.75 倍）"——
> 一眼就定位到"单位换算多乘了密度"。

**2. 滑块外面套手势处理器会让它彻底拖不动。**

为了给撤回栈标记"操作开始"，我在滑块外套了一个 `pointerInput`，
一按下就调 `onBegin()`。结果那个处理器与 Slider 自己的手势竞争，
`awaitFirstDown` 拿到事件后，后续移动不再可靠地送给 Slider ——
**所有滑块都拖不动，连开关也是**。

改成用 `onValueChange` 的首次回调去重标记开始、`onValueChangeFinished` 收尾，
Slider 的手势完全不插手。

> 规矩：**不要为了"顺便做点别的事"而包住一个交互控件的手势**。
> 用它的回调，别抢它的事件。

**3. 属性面板在最下面 → 改文本时被软键盘盖住。**

加了 `imePadding()`（Activity 本来就是 `adjustResize`）。

**4. 画布预览算错尺寸会变成一个盖住整页的 `Box`，吃掉所有触摸。**

这是"整个编辑界面几乎都是死的"的**另一半**原因（另一半是第 5 条的状态问题）：
预览把倍率算成了像素比值，于是那个"画布"实际上有几千 dp 宽，
虽然看不见（没画背景），但它**参与命中测试**，
铺在属性面板与组件条之上 —— 表现正是"只有顶栏和组件条能用"。

现在预览让 `CustomKeyCanvas` 自己按 dp 倍率出尺寸，外层 `Box` 只是
"虚线框 + 选中框"的容器，两者用同一个尺寸；`BoxWithConstraints`
的约束还会把它夹在可用空间内。

> 排查提示：**看不见的视图也能吃掉触摸**。一个尺寸算错的 `Box`/`Canvas`
> 完全不会显示异常，但会把下层控件全部挡死。

### 关于 `resetParamsToDefault` 里**故意不列 custom**

那份函数是一张"必须枚举全部字段"的清单，漏一个就是"某个设置重置不掉"。
但这里的判断标准是**"它是参数，还是用户的创作"**：

- 颜色/缩放/动画 → 参数，重置；
- **组件布局 → 用户的创作**，抹掉它等于删了用户的成品。

所以自定义布局的重置**单独放在编辑器的「恢复默认布局」按钮上**，
让用户明确知道自己要丢掉什么。加新字段时请照着这个标准判断。

## 5. 两个占位符的坑（有测试钉着）

`formatCpsTemplate` 的"隐藏"语义是**整段返回空字符串** ——
那是给 Key 样式模式 1 设计的，因为**那边的模板里就只有占位符本身**。
文本组件里模板可能带别的文字，直接套用会出两种错：

1. 对一份普通文本调用 `hideWhenZero` → 把整段文字清掉（显示成空）；
2. `CPS: (cps2)` 为 0 时 → 连 `CPS:` 一起抹掉，而用户只想让数字消失。

所以 `CustomLayout.resolveText` 是**按出现的占位符二选一**，
并且 `(cps2)` 为 0 时只替换掉占位符那一段，最后 `trim()` ——
去掉占位符会留下一个孤零零的空格，让文字看起来偏左，
而"多一个空格造成的位移"正是用户要拿文字偏移去救的东西，不该由我们自己制造。

## 7. 已知风险

1. **布局可能比屏幕还大**：画布固定 600×600，再乘整体缩放，
   在小屏上可能超出可用区域 —— 超出部分是看不见的（窗口侧有边界夹取，
   见 `docs/multi-overlay.md` 7.7 第 1、2 条）。
   规避办法是把整体缩放调小，或者在画布里把组件摆得紧凑些。
2. **文字可能超出组件边框**：文字偏移与放大字号都可能让它溢出。
   目前不做自动裁切，错了就自己调。
3. **组件可以有一部分在窗口外**：坐标允许落到负值（这就是"贴边"的用法）。
   完全移出窗口的组件在悬浮窗上看不见，但编辑器里仍然能看到并改回来。
4. **没有吸附对齐**：只有滑块与「居中」，想把两个组件对齐得自己算坐标。
   （滑块精确到 1 个单位，所以这不是"对不齐"，只是要多点几下。）
5. **复制是"完全一样"的**：不做自动改名。连续复制同一个模板时，
   画布上会有几个文字相同的组件 —— 它们靠位置区分，编辑时注意别选错。
6. 组件数量没有上限。每个组件都是一次 Compose 绘制，几十个没问题，
   上百个在低端机上可能掉帧 —— 与"多开悬浮窗"同一类风险。
7. **侧栏宽度是固定 330dp**：在极窄的窗口（分屏、小屏横屏）上会占掉一大半宽度，
   留给画布的空间很少。这时应该切回「下」。
8. **没有真机验证过**。本机没有连设备（`adb devices` 为空），
   目前这版编辑器的保证只有：编译通过 + 73 条单元测试全绿。
   所有"手点才能发现"的问题（响应是否跟手、滑块手感、键盘遮挡、
   平板上侧栏的观感、多选对话框的手感）都还没有被验证过。
