# 图片字体（Minecraft 风格位图字体）

这份文档是**图片字体**子系统的设计依据：格式规范、数据模型、
为什么这么做、哪里不能改。改动这个子系统之前先读这里，改完如果契约变了，回来同步。

> **实现状态**：已完成（v2.4.0）。
> 第 2 节是**外部格式规范**（来自 Minecraft Wiki 与原版真实数据，不要改）；
> 第 3~9 节是**我们的实现与取舍**；
> 第 10 节是**踩过的坑**，改动前必读。

---

## 0. 一句话说清它是什么

在矢量字体（TTF）之上**叠一层可选的位图字体**：

| | 常规字体（矢量） | 图片字体（位图） |
|---|---|---|
| 必选？ | **必选**，中文由它兜底 | **可选**，只覆盖 ASCII |
| 存哪 | `fontId` | `bitmapFontId` |
| 能画什么 | 任意文字 | 只有 ASCII |
| 特色 | 缩放到任意字号都清晰 | **能做到渐变、描边、发光** |

> ⚠️ 两者**不是二选一**。图片字体只有 ASCII 字形，中文必须由常规字体兜底 ——
> 所以是"**常规字体（必选）+ 图片字体（可选）**"，界面上也是两个独立入口。
>
> 早先合成一个单选框做二选一，后果是选了图片字体之后中文没有退路
> （回落到系统默认，而不是用户选的字体），而配置里只有一个 `fontId`，
> 根本表达不了"两个都要"。

---

## 1. 为什么做这个

TTF/OpenType 是**矢量字体**：一个字形只有轮廓和填充，**做不出材质包里那种
自带渐变、描边、发光、内阴影的像素画**。而 Minecraft 生态的字体恰好是
**位图图集**——每个字符是一小块像素画，想怎么画就怎么画。

于是需求是：**在现有 TTF 逻辑之上，加一层位图字体，只处理 ASCII**。

> **中文不做**，仍然交给 TTF。理由：中文有上万个字，位图图集需要一张一张画，
> 不现实；而且中文用矢量字体在缩放时的表现明显更好。

## 2. 外部格式规范（Minecraft Java 版）

来源：[Minecraft Wiki – Font](https://minecraft.wiki/w/Font)、
[Bitmap provider](https://minecraft.wiki/w/Font#Bitmap_provider)、
以及原版 `assets/minecraft/font/include/default.json` 的真实数据。

### 2.1 字体定义文件

```json
{
  "providers": [
    { "type": "bitmap", "file": "minecraft:font/ascii.png",
      "ascent": 7, "chars": [ "…16 个字符串，每个 16 个字符…" ] }
  ]
}
```

| 字段 | 必填 | 默认 | 含义 |
|---|---|---|---|
| `type` | 是 | — | `"bitmap"` |
| `file` | 是 | — | PNG 路径 |
| `ascent` | 是 | — | 格子顶边在**基线上方**多少像素（输出像素） |
| `chars` | 是 | — | **字符串列表**：每个字符串一行，每个字符一列 |
| `height` | 否 | **8** | 字形的**目标高度**（缩放后），不是纹理高度 |

### 2.2 三个必须照做的规则

**① 行数/列数由 `chars` 决定，不由图片决定。**

规范里**没有** `rows` / `columns` 字段。列数 = 最长字符串的长度，行数 = 字符串个数。
格子 = `图宽 ÷ 列数` × `图高 ÷ 行数`，**均分、无间隔、无外边距**。

⚠️ 一条行多一个字符，就会改变整张图的列数、把**每一个字都切错**。
所以导入时必须校验 `图宽 % 列数 == 0` 且 `图高 % 行数 == 0`，除不尽就直接报错。

**② 推进宽度不是格子宽度，而是扫描出来的。**

> "The glyphs' widths are automatically determined based on the last right-most
> column of pixels containing any alpha value above 0"

即 **`推进宽度 = 最右非透明列 + 2`**（墨迹宽 + 1 像素间隔）。

证据：原版 `█`（全块）在 **8 像素**的格子里推进 **9** 像素；`▌`（半块）推进 5;
`i` 推进 2、`l` 推进 3、`W` 推进 6。

**这是本功能的关键规则**——不扫描像素的话，等宽格子里每个字符都会等宽，
`i` 和 `W` 一样宽，排版会非常难看。

> 扫描时**透明像素必须是 `(0,0,0,0)`**：基岩版有个已修 bug（MCPE-17913），
> 透明背景不是纯黑时宽度算错。我们的扫描要容忍这一点（只按 alpha 判断）。

**③ 基线位置：格子顶边 = 基线 − `ascent`。**

原版 `ascii.png` 是 8 像素格、`ascent = 7`，所以格子底边**比基线低 1 像素**——
那一行留给 `g`、`y`、`p` 这类下伸字母。`ascent` 允许大于 `height`（图标字体的常见做法）。

### 2.3 `ascii.png` 的**截取算法**（本功能的地基，已逐格验证）

#### 权威依据

原版 `assets/minecraft/font/include/default.json` 里 `ascii.png` 的 `chars`
字段直接给出了**全部 256 格**的字符映射（节选，`\u0000` 是我加的注释）：

```
chars[0]  = 16 × \u0000                                    ← 填充
chars[1]  = 16 × \u0000                                    ← 填充
chars[2]  = U+0020 U+0021 … U+002F      // 空格 ! " # $ % & ' ( ) * + , - . /
chars[3]  = U+0030 … U+003F             // 0-9 : ; < = > ?
chars[4]  = U+0040 … U+004F             // @ A-O
chars[5]  = U+0050 … U+005F             // P-Z [ \ ] ^ _
chars[6]  = U+0060 … U+006F             // ` a-o
chars[7]  = U+0070 … U+007E, 末位 \u0000 // p-z { | } ~
chars[8]  = 16 × \u0000                                    ← 填充
chars[9]  … chars[15] = CP437 符号区（£ ƒ ª º ─ │ ┌ ░ ▒ ▓ █ ▌ ▐ ■ 等）
```

#### 算法

```
列数 = 16，行数 = 16                    （由 chars 决定，不由图片决定）
格宽 = 图宽 ÷ 16，格高 = 图高 ÷ 16       （必须整除，否则整张图切错）

对 ASCII 码点 code ∈ [0x20, 0x7E]：
    index = code - 0x20
    row   = 2 + index / 16              ← 注意这个 +2
    col   = index % 16
    格子   = x ∈ [col×格宽, (col+1)×格宽),  y ∈ [row×格高, (row+1)×格高)
```

**`+2` 是最容易错的一步。** 第 0、1 行是填充位（原版那两行在图里画的是控制符图形），
ASCII 从**第 2 行**才开始。按"从第 0 行开始"去核对，会得到
"空格那一格有墨水"这种荒谬结果，进而误判成"这张图不是这个格式"。

#### 逐格验证结果（原版 `ascii.png`，128×128 / 8×8 格）

以下为**实测**，并与 Minecraft Wiki 的官方宽度表逐项吻合：

| 字符 | 格 (col,row) | 墨迹 x | 墨迹 y | 墨迹宽 | 推进 = 墨迹宽+1 |
|---|---|---|---|---|---|
| `space` | (0,2) | 空白 | 空白 | 0 | —（单独给 4） |
| `!` | (1,2) | 0..0 | 0..6 | 1 | 2 |
| `"` | (2,2) | 0..3 | 0..2 | 4 | 5 |
| `,` | (12,2) | 0..0 | 5..7 | 1 | 2 |
| `-` | (13,2) | 0..4 | 3..3 | 5 | 6 |
| `0`…`9` | (0..9,3) | 0..4 | 0..6 | 5 | 6 |
| `:` | (10,3) | 0..0 | 1..6 | 1 | 2 |
| `@` | (0,4) | 0..5 | 0..6 | 6 | 7 |
| `A`…`H` | (1..8,4) | 0..4 | 0..6 | 5 | 6 |
| `I` | (9,4) | 0..2 | 0..6 | **3** | 4 |
| `W` | (7,5) | 0..4 | 0..6 | 5 | 6 |
| `_` | (15,5) | 0..4 | **7..7** | 5 | 6 |
| `a` | (1,6) | 0..4 | **2..6** | 5 | 6 |
| `f` | (6,6) | 0..3 | 0..6 | 4 | 5 |
| `g` | (7,6) | 0..4 | **2..7** | 5 | 6 |
| `i` | (9,6) | 0..0 | 0..6 | 1 | 2 |
| `j` | (10,6) | 0..4 | 0..**7** | 5 | 6 |
| `l` | (12,6) | 0..1 | 0..6 | 2 | 3 |
| `t` | (4,7) | 0..2 | 0..6 | 3 | 4 |
| `~` | (14,7) | **0..5** | **0..1** | 6 | 7 |

**从这张表能读出四条规则，全部与规范一致：**

1. **推进宽度 = 墨迹宽 + 1**：官方表说 `!`=2、`@`=7、`A`=6、`I`=4、`~`=7，
   而实测墨迹宽正好都比它们少 1。这是"扫描像素"规则的直接证据。
2. **字形左对齐**：所有字符的墨迹都从格内 `x = 0` 开始，右侧留白由格宽决定。
3. **基线在格内偏移 6**：非下伸字符占 `y 0..6`；
   下伸字符（`g j p q y`）占 `y 2..7`；下划线 `_` 单独在 `y 7`。
   即**基线之下还有 1 行的空间**——这正是 `ascent = 7`、格高 8 的由来。
4. **空格是空白格**：原版在 `ascii.png` 里给 U+0020 留了一个**完全透明**的格子，
   所以扫描只能得到 0 宽。**原版为此额外挂了一个 `space` provider**（`" ": 4`）。
   → 我们直接给空格一个固定推进宽度，不指望从图里扫。

#### 其他已实测的图

它们都是同一张 128×128 逻辑位图的整数倍放大，网格与相位完全一致：

| 图 | 原生 | 缩放 | 格（原生像素） | 取遮罩 |
|---|---|---|---|---|
| Java 原版 | 128×128 | 1× | 8×8 | `ALPHA` |
| 材质包高清 | 512×512 | 4× | 32×32 | `ALPHA` |
| 材质包平滑字体 | 256×256 | 2× | 16×16 | **`LUMINANCE`**（见第 3 节） |
| 基岩版 default8 | 128×128 | 1× | 8×8 | `ALPHA` |

⚠️ 四张图中**没有任何一列**是完全透明的，说明格子**严格相邻、无分隔线、无外边距**。
不要试图"找分隔线"来切格子。

⚠️ 「高清」指的是**分辨率**，不是抗锯齿：它的 alpha 依然只有 0/255，
没有任何中间值。只有「平滑字体」那张是抗锯齿的——而它的墨水**不在 alpha 里**（见第 3 节）。

### 2.4 原版 `ascii.png` 的槽位排布（背景知识）

- 槽位整体遵循 **CP437 码页**顺序，全图 256 格；
- ASCII `0x20..0x7E` 占第 2~7 行；第 0、1 行与第 8 行是**填充**；
- 第 9~15 行是 CP437 的符号区：`£`(0x9C)、`ƒ`(0x9F)、`ª` `º` `¬` `«` `»`、
  制表符 `─ │ ┌ ┐ └ ┘ ├ ┤ ┬ ┴ ┼`、块元素 `░ ▒ ▓ █ ▄ ▌ ▐ ▀`、`≡ ± ≥ ≤ ÷ ≈ ° ∙ √ ⁿ ² ■`、
  以及原版替换掉 CP437 的 `∅`(0xED)、`∈`(0xEE)；
- **`\u0000` 是"占位"标记**：该格不算作任何字符。原版用它跳过了旧 CP437 的
  重音字母与希腊字母（那些已移到 `accented.png` / `nonlatin_european.png`）。

> **本功能只取 ASCII**，所以这些符号区暂时用不到。记在这里是为了说明
> "为什么 ASCII 不从第 0 行开始"——因为第 0、1 行本来就不是 ASCII 的位置。

| 图 | 原生 | 缩放 | 格（原生像素） | 取遮罩 |
|---|---|---|---|---|

| 材质包高清 | 512×512 | 4× | 32×32 | `ALPHA` |

- 格子**严格相邻，无分隔线、无外边距**（四张图中**没有任何一列**是完全透明的），
  所以**不要试图"找分隔线"来切格子**；
- **字形左对齐**（墨迹从格内 x=0 开始）；

- 墨迹宽度众数是 **5**，范围 1（`|`）~ 6（`@` `~`）。

「原版」与「基岩版」**97.5% 像素相同**（只差 14 个格子：基岩版多画了些符号），
可视为同一套字形；「平滑」与「高清」是**另一套相关字形**（与原版 IoU 约 0.7）。

## 3. 两种取遮罩的方式（**这是最容易踩的坑**）

四张图的像素构成**不是同一种**：

| 图 | alpha 取值 | 墨水承载在 | 性质 |
|---|---|---|---|
| Java 原版 | 只有 0 / 255 | **alpha** | 1-bit 像素画 |
| 基岩版 default8 | 只有 0 / 255 | **alpha** | 1-bit 像素画 |
| 材质包高清 | 只有 0 / 255 | **alpha** | 1-bit 像素画（"高清"指分辨率，**不是**抗锯齿） |
| **材质包平滑字体** | **只有 0 / 255** | **RGB 灰度** | 白底 + 21 级灰度，抗锯齿 |

### 平滑字体的陷阱

那张"平滑"图是：**白色背景（RGB 255）、字形用 21 级灰度（208~255）画**，
而 alpha 通道是个**被二值化的遮罩**（`alpha = 255 − 灰度`，且在 2×2 块内完全一致）。

按常规读法（`alpha > 0` 即墨水、RGB 当颜色）会得到：

- 整格 `alpha = 255` → **遮罩全满**；
- RGB 全是白色 → 染成用户颜色后是**一坨实心方块**；
- 21 级渐变**全部丢失**。

**所以必须区分两种取遮罩的方式：**

| 模式 | 遮罩计算 | 颜色 |
|---|---|---|
| `ALPHA` | `coverage = alpha` | 由用户指定（字形 RGB 与之相乘） |
| `LUMINANCE` | `coverage = 255 − 亮度` | 由用户指定（丢弃图片自身的白/灰） |
**自动判别**（导入时给个默认值，但**必须允许手动改**）：

- `alpha = 0` 的像素占比 > 50% → `ALPHA`；
- 否则若 `alpha = 255` 占绝大多数、且 RGB 集中在一个窄的高亮区间 → `LUMINANCE`。

⚠️ 判错的后果是"整块白块"这种**一眼看不出原因**的现象，所以界面上要能手动切换并实时预览。

## 4. 颜色模型

规范写得很明确：**字形 RGB 与文字颜色相乘**。

- 白色字形 → 完全跟随「文字颜色」✓（这是想要的效果）
- 彩色字形 → 保留色相
- 黑色字形 → 永远黑

**所以不需要"保留原色"开关**，乘法语义天然覆盖三种情况。

> **具体实现（含"为什么不能用 `ColorFilter.tint` 的默认值"）见 6.6** ——
> 那里还讲了渐变为什么会被毁掉、以及抠洞层为什么要反过来用 `SrcIn`。

界面要提示一句：**"白色字形才能自由染色"**——避免用户拿彩色图集来用，
然后奇怪为什么颜色调不动。

## 5. 与 TTF 混排（**尚未实现**）

> ⚠️ **本阶段只做纯 ASCII**：一段文字里只要出现图片字体画不了的字符
> （中文等），**整段**回退矢量字体。判据集中在 `canRenderAsBitmap()` 一处。
>
> 下面记的是**以后要做混排时的思路**，不是现状。

需求是"**ASCII 走图片、中文走 TTF**"，所以同一行文字里两种字形要混排。

### 5.1 为什么不能用 `SpanStyle`

Compose 的 `SpanStyle` 只能改**样式**（颜色、字号、字体族），**没法把某个字符
替换成一张 Bitmap**。没有内置的"按字符替换字形"机制。

### 5.2 若要做，采用的办法：测量 + 定点绘制

1. 用 `TextMeasurer` 量出整行文字，拿到**每个字符的 x 坐标**；
2. ASCII 部分**逐个把位图画在对应位置**；
3. 非 ASCII（中文等）留给 TTF 正常渲染；
4. 两边**共用 TTF 的行高与基线**，所以混排时不会一个高一个低。

**好处**：描边、文字阴影、按下变色这些现有逻辑**全部不用重写**——它们作用在
"整块文字"上，位图字体只是把其中一部分字形换掉了。

### 5.3 需要注意的点

- **基线对齐**：位图格子按 `ascent` 定位到基线，与 TTF 的基线一致；
- **行高**：位图字形高度可能与 TTF 不同，行高应取两者较大值，否则会重叠；
- **空格**：位图图集里空格是"声明了但格子空白"的情况，推进只有约 1 像素
  （原版必须额外挂一个 `space` provider 给 `" ": 4`）。**我们直接给空格一个固定宽度**，
  不能指望从图里扫出来。

⚠️ 做混排时最容易出错的是**按字符切分后共用基线**：两套字体的行高与基线假设不同
（图片字体是"格子底边比基线低 1 像素"，TTF 是按升降部居中），
一个偏一点就会看起来"一行字高高低低"。现在的 `verticalNudge` 只解决了
**纯 ASCII** 那一档；混排要重新校一遍。

## 6. 缩放与滤镜

### 6.1 像素对齐

8×8 的像素字在 35px 下显示，倍率是 **4.375**——**非整数**。Minecraft 里字体按整数倍
缩放，所以棱角分明；非整数倍会让像素边缘变粗变糊、粗细不均。

方案：

- **默认**：与现有字号逻辑联动，任意缩放（保持滑块连续可调）；
- **提供"像素对齐"开关**：开启后把倍率吸附到最接近的整数倍，最锐利。

⚠️ 不要强制整数倍：那会让用户以为字号滑块坏了。

### 6.2 滤镜

像素画用双线性插值放大必糊，所以 `ALPHA` 模式用 `FilterQuality.None`；
`LUMINANCE` 那种抗锯齿图集反过来要用低通。**这是每个字体各自的属性，不能全局定死。**

### 6.3 ⚠️ 缩放基准是"墨迹高度"，不是声明的 `height`

**用户实测的问题**：不同分辨率的图集（128 / 256 / 512）**初始大小不统一**。

**根因**：不同材质包对同一个 `height` 的**留白习惯不同** —— 有的字形占满声明的行高，
有的只占六成。按声明高度归一化，结果就是"同样字号下这个字体比那个大一圈"。

**做法**：按**实际墨迹**归一化 —— 量出"典型非下伸字形"的高度中位数
（[`referenceInkHeight`]），把它映射到 `0.7 × 字号`。

为什么取中位数而不是量 `A`：不同图集里 `A` 这类字符可能只有几十个像素、
也可能是空格，中位数对个别异常图元更稳。

为什么是 `0.7`：图集里的字形高度**不含行距**，而字号对应的是 TTF 的 em 尺寸
（含上伸、下伸与行距）。大写字高在多数 TTF 里约占 em 的 0.7。

**实测验证**（四张图集）：

| 图集 | 原生尺寸 | 格 | 参考墨迹 | 墨迹/格 |
|---|---|---|---|---|
| java 原版 | 128×128 | 8×8 | **7** | 7/8 |
| 基岩版原版 | 128×128 | 8×8 | **7** | 7/8 |
| 材质包高清 | 512×512 | 32×32 | **28** | 7/8 |
| 材质包平滑 | 256×256 | 16×16 | **14** | 7/8 |

四张图的墨迹高度**都是格高的 7/8**，所以归一化后它们画出来必然一样大。

### 6.4 垂直位置与"文字偏移"

Minecraft 的基线约定是"格子底边比基线低 1 像素"（格高 8、ascent 7），
而 TTF 在 `lineHeight = fontSize` 的行盒里是按**字体自身的升降部**居中 ——
两者对"文字该落在哪"的假设不同，于是图片字体看起来会**整体偏上**。

补偿量可以从实测推出来：

```
TTF  : fontSize/2 + 0.35×fontSize = 0.85 × fontSize
位图 : 7/16 × 格高 + 7/8 × 格高 ≈ 0.5 × fontSize
差值约 0.1 × fontSize，而渲染后墨迹高 0.7 × fontSize → 约 14%
```

⚠️ 但 TTF 的"下伸 0.2em"是**上限**而不是常规文字的实际情况
（`LMB`、`W` 这类键名根本没有下伸字母），按 14% 补偿会推过头。
**折中取 `verticalNudge = 7.5%`**（[`BitmapFontSpec.verticalNudge`]）。

⚠️ 这个值**不可能有唯一正确答案**，因为它取决于"那个配置里的文字长什么样"。
所以真正的解法是**给用户可调的文字偏移**：

| 层级 | 字段 | 说明 |
|---|---|---|
| 全局 | `KeyStrokesConfig.textOffsetX/Y` | 整体挪 |
| 每个键 | `KeyStrokesConfig.slotTextOffsets[slotId]` | 单独修个别键 |

**为什么必须有"每个键"**：用户实测的场景 —— 空格位显示的是 `————` 这种
**非 ASCII** 横线，它不会被图片字体替换（图片字体只有 ASCII 字形），走的是矢量字体。
两种字体的基线位置不同，全局调好之后那些**真正用图片字体画的键**就偏了。

⚠️ 偏移的**单位与自定义 Key 的文字偏移完全一致**（基础坐标单位），
所以"Key → 自定义"转换是**原样搬运**，转换后位置不会跑偏。
范围也照抄（−60..60）。

⚠️ **偏移必须在同一个 `KeyLabel` 层上统一生效**。阴影要画三遍
（阴影本体、抠洞、正文），三遍必须逐像素对齐；偏移若在不同地方各算，
只要有一处漏了，抠洞就会擦错位置 —— 表现是"文字边上缺一块"。

### 6.4.1 字间距与行间距

与文字偏移**同一套结构**（全局 + 每槽位），在界面上也挨着放：

| 层级 | 字段 | 范围 |
|---|---|---|
| 全局 | `KeyStrokesConfig.textSpacing` | −50..100 / −50..200 |
| 每个键 | `slotTextSpacings[slotId]` | 同上 |

自定义 Key 那边是组件样式上的两个字段（`letterSpacing` / `lineSpacing`）——
组件本身就是独立对象，不需要再按槽位查表。

**单位是"相对字号的百分比"，不是像素/dp。** 字号是可调的（文字缩放 + 整体缩放），
固定像素值在小字号下会挤成一团、大字号下又几乎看不出来。百分比天生跟着字号走。

⚠️ **两种字体都要吃这两个值**，这是刻意的：
"字距不合适"在**矢量字体**上同样会发生（中文字体尤其常见），
早先只接了图片字体那条路，表现就是"调了完全没反应"。

| 路径 | 字间距 | 行间距 |
|---|---|---|
| 矢量（`KeyGrid` / `CustomKeyGrid`） | `TextStyle.letterSpacing`（单位 **em** → 除以 100 正好对上） | 行高 × 系数 |
| 图片字体（`BitmapFontText`） | 推进宽度（要除以 `pixelScale` 换回图集像素） | 行高 × 系数 |

⚠️ 行距**有下限**（`MIN_LINE_SPACING_FACTOR = 0.5`）：调到 0 会让两行直接重叠，
那不是"紧凑"而是坏了。三条绘制路径**共用同一个常量** ——
各写一份的话，同一个滑块在两种字体下能收到的下限不一样，用户会以为是哪一个坏了。

⚠️ 行距是**乘进行高**，不是插 `Spacer`。行高本来就显式等于字号，
所以"行距 = 行高 × 系数"就是把行间基准距离拉开，而且**首行之前不会多出空白**
（插 Spacer 还得特判首行，否则整块文字会下移，看起来像"偏移被改了"）。

### 6.5 阴影

**硬阴影**：原版 Minecraft 的做法 —— 文字右下方一份实心副本。
用外层 `graphicsLayer` 的位移实现。

**柔光**：`API 31+` 用**真模糊**（`Modifier.blur`，底层 `RenderEffect`）：

```
模糊先作用于阴影副本 → 抠洞再擦掉中心 → 留下真正的光晕
```

⚠️ 顺序是关键。早先用的是"画 8 个偏移副本、每层降透明度"的近似，
**但在这个场景下上限不高**：柔光那一层画完副本后还要用 `DstOut` 把字形本身擦掉，
剩下的只是"字形外面一圈薄晕"；而图片字体是**像素块** ——
块状字形外一圈薄晕看起来就是硬阴影。

⚠️ `BlurredEdgeTreatment.Unbounded` 是必须的：默认的 `Rectangle` 会把模糊
**裁在组件边界内**，光晕只出现在内容里面、外面一圈全切掉，看起来就是"没生效"。

⚠️ `Modifier.blur` 收 **Dp**，而 `BitmapFontText` 的参数是**像素**。

⚠️ **API 30 没有 `RenderEffect`**，那时退回多层副本（见 `ui/overlay/RealBlur.kt`）。
两条路**互斥** —— 同时上会糊成一团，还白画 8 遍。

### 6.6 颜色与渐变

Minecraft 的染色语义是**字形 RGB 与文字颜色相乘**（`BlendMode.Modulate`）。

| 字形 | 效果 |
|---|---|
| 白色 | 变成文字颜色 |
| **渐变** | **渐变完整保留**，整体被文字颜色染色 |
| 彩色 | 保留色相 |

⚠️ **不能用 `ColorFilter.tint(color)`**：它的默认混合模式是 **`SrcIn`** ——
**只看 alpha、完全忽略输入 RGB**，等于"把整块换成纯色"。对纯白字形看不出区别，
但会**毁掉渐变**，而"能显示渐变"正是引入图片字体的主要理由之一。

⚠️ **抠洞层（`DstOut`）反过来必须用 `SrcIn`** 画成**实心剪影**：
它按源的不透明度擦除，而渐变字形的浅色部分不透明度低，抠出来就是一圈毛边。

⚠️ `LUMINANCE` 模式的图集（白底灰字）在**加载时**就被转成
"白色墨迹 + alpha 覆盖率"，所以渲染层可以统一用 `Modulate`，不必分情况。

## 7. 数据模型与代码结构（实际实现）

### 7.1 分层：纯逻辑 / Android / 渲染 / 界面

```
domain/font/bitmap/
  BitmapFontAtlas.kt     纯逻辑：切格子、扫字形、算推进宽度、取遮罩
  BitmapFontSpec.kt      规格（网格 / 遮罩 / ascent / 微调）+ JSON 持久化
  BitmapFontStore.kt     Android：图集解码、字形缓存、导入/删除/改名、去重
  BitmapFontImporter.kt  Android：从 .png / .zip / .mcpack 取出图集

ui/overlay/BitmapFontText.kt   渲染：排版（纯函数）+ 逐字贴图
ui/component/FontPicker.kt     两个字体选择对话框（常规 / 图片）
ui/component/BitmapFontImportDialogs.kt  导入命名流程
ui/component/SlotTextOffsetDialog.kt     每个键各自的文字偏移
```

> ⚠️ **纯逻辑层不碰 Android 的 Bitmap**：它通过 `PixelSource` 接口拿像素，
> 测试里塞一个内存数组就能跑。于是"数格子、扫字形、算宽度"这些
> **最容易错、错了最难查**的东西全部能在单测里穷举。

### 7.2 关键类型

```kotlin
/** 怎么切格子（对应 Minecraft 的 chars 字段语义） */
data class AtlasGrid(
    val columns: Int,
    val rows: Int,
    val firstCodePoint: Int = 0x20,   // 从空格开始
    val firstColumn: Int = 0,
    val firstRow: Int = 2,            // ⚠️ 第 2 行，不是第 0 行
)

/** 一张图片字体的规格（可持久化） */
data class BitmapFontSpec(
    val atlasFileName: String,
    val grid: AtlasGrid,
    val codePoints: List<Int> = DEFAULT_ASCII,  // 0x20..0x7E 共 95 个
    val height: Int = 8,
    val ascent: Int = 7,
    val maskMode: MaskMode = MaskMode.ALPHA,
    val widthInCells: Int = 1,
    val pixelAlign: Boolean = false,     // 是否吸附整数倍缩放
    val tinted: Boolean = true,          // 是否跟随文字颜色
    val verticalNudge: Float = 7.5f,     // 垂直微调（渲染后墨迹高度的百分比）
)

/** 扫出来的一个字形（坐标相对基线） */
data class Glyph(
    val codePoint: Int,
    val srcX: Int, val srcY: Int, val srcWidth: Int, val srcHeight: Int,
    val top: Int,        // 相对基线的顶边（负值在基线上方）
    val advance: Int,    // 推进宽度 = 墨迹右边界 + 2
    val hasInk: Boolean,
)
```

**派生数据**（加载时扫一次、按 id 缓存）：字形表。
⚠️ **必须缓存**：一张 512×512 的图集要遍历 26 万像素，而渲染是每帧都在跑的。

## 8. 导入流程

### 8.1 三种来源

| 来源 | 扩展名 | 找什么 | 为什么 |
|---|---|---|---|
| 单张图片 | `.png` 等 | **不检查**，直接用选中的文件 | 用户可能已经把 `ascii.png` 改过名、或从材质包里单独抠出来 |
| Java 材质包 | `.zip` | 包内任意位置的 **`ascii.png`** | Java 版放在 `assets/<ns>/textures/font/`，但包结构千奇百怪 |
| 基岩版材质包 | `.mcpack` | 包内任意位置的 **`default8.png`** | 基岩版主 ASCII 图集就叫这个名 |

⚠️ **按文件名在整个压缩包里递归找**，不写死路径 —— 实测材质包的目录层级并不统一
（有的多一层 `assets/minecraft/`、有的直接摊在根目录），写死会让相当一部分包导入失败。

⚠️ **按扩展名分派，按 MIME 不行**：SAF 对 `.mcpack` 这类扩展名常返回
`application/octet-stream`（认不出来），而 `.zip` 与 `.mcpack` 的字节结构完全一样 ——
光看 MIME 分不清该找 `ascii.png` 还是 `default8.png`。

⚠️ 压缩包读取**带大小上限**：zip 条目声明的大小可以被伪造得很小而实际解出很大
（压缩炸弹），所以边读边计数，超了立刻停。

### 8.2 先试解码再登记

用户可能选错文件（随手一张照片，或压缩包里那个**同名但不是字体图集**的文件）。
直接登记的话条目会存下来、但**永远画不出东西**，界面上只会显示"这个字体没效果"。

所以先按规格真解一遍：解码失败、或**图宽装不下网格**，都当场拒绝并把原因说清楚
（"图片尺寸 512×512 装不下 16×16 的网格"）。

### 8.3 必须让用户命名

MC 的字体图集**几乎都叫 `ascii.png`**（基岩版叫 `default8.png`）。用文件名当字体名的话，
导入几张之后列表里全是同名条目。默认值给**导入时刻**（`yyyyMMddHHmmss`），
用户直接确定也行。

### 8.4 ⚠️ 还没有的：规格校准界面

目前导入时用的是**原版 `ascii.png` 的规格假设**（16×16 格、ASCII 从第 2 行第 0 列起、
`height 8`、`ascent 7`），遮罩模式**自动猜**。

而实际材质包的规格可能不同 —— 尤其 `ascent` 因图而异，**基线位置差一点就会整体偏上/偏下**。
现在的应对是"每个键各自的文字偏移"（见 6.4），但**改不了 `ascent` 本身**。

要支持非原版规格的图集，需要做这个界面：可调 `列数 / 行数 / 起始字符 / 起始格 /
height / ascent / 遮罩模式 / 像素对齐`，并**实时预览校验**。

> 为什么预览校验是必须的：映射错了的表现是"**字全错位但看不出哪错了**"，
> 光看图集很难发现，等用起来才发现就太晚了。

## 9. 配置包（导出 / 导入）

### 9.1 规格必须"跟着包走"

矢量字体只要带文件就够（字体文件自带全部信息）。**图片字体不行**：

> 配置里只存了一个 `bitmapFontId` —— "怎么切格子、怎么取遮罩、ascent 多少"
> 这组参数存在**导出方的字体库里**。

所以只带一张 PNG，导入方拿到也不知道该怎么解析。而图片字体的规格恰恰是
**因图而异**的（不同材质包的行列数、遮罩模式、`ascent` 都可能不同），猜一套默认值必然出错。

**做法**：把 `BitmapFontSpec` 的字段**平铺**进 manifest 的字体条目里
（`ConfigPackageCodec.FontFileInfo.bitmap`）。

为什么平铺而不是套一层 `"bitmap": {...}`：`BitmapFontSpec.fromJson` 本来就是按
"从同一个 JSON 对象里读这些字段"写的（字体库里也这么存），平铺之后
**读写共用同一段逻辑**，不会出现两处字段名不一致。

**判断"是不是图片字体"看 `maskMode` 在不在** —— 不加 `kind` 字段。
少一个要维护的枚举，也不会出现"kind 说是矢量、实际带着一整套图片规格"这种自相矛盾的条目。

### 9.2 文件与目录

图片字体的图集和矢量字体**放同一个目录** `assets/fonts/`，靠后缀区分（`.png` / `.ttf`）。
这样导出/导入/清理都能走同一套逻辑，少一处分支就少一处"只有某种字体才会出问题"的 bug。

⚠️ 用了图片字体的包会比以前大一些（一张 `ascii.png` 通常几十 KB，
512×512 的高清图集则多几百 KB）。

### 9.3 ⚠️ `bitmapFontId` 字段名是**有意的**

配置包的字体改写靠 `ParamsTree` 扫"名字以 `fontId` 结尾的字段"
（`isFontKey()` 检查 `== "fontId"` 或 `endsWith("FontId")`）。

所以叫 `bitmapFontId` 就**自动被收集和改写**，不必改那套逻辑。
**新加字体类字段时沿用这个命名约定。**

### 9.4 去重

导入时按**图集内容哈希 + 规格**判断本地是不是已经有了。

比矢量字体的判据强：除了内容相同，还要求**规格也相同** ——
图一样但网格不同就是两个字体。

⚠️ 所以 `BitmapFontStore.Entry` 里存了 `sha256`，普通导入时也要记
（否则"先手动导入、再从包导入"会存两份）。

### 9.5 ⚠️ `KNOWN_KEYS` 是推导出来的

`JsonConfigCodec.KNOWN_KEYS` 不是手写清单，而是**把探针配置编码一遍、
看写出了哪些键**推导出来的。

**后果**：任何"条件写入"的字段（`if (非空) put(...)`）都可能**不在已知清单里**，
于是带这个字段的配置包导入时被报成"未识别字段" —— 明明能正常读写，却被说不认识。

`slotTextOffsets` 就踩过这个坑。**新增字段时一律无条件写**
（空值也写），换来的是"读写对称 + 键始终已注册"。

## 11. 已知的坑（**改动前必读**）

### 11.1 格式与算法

1. **ASCII 从第 2 行开始**，不是第 0 行。搞错会得到"空格那格有墨水"这种结果，
   进而误判成"格式不匹配"。（这个坑我在这里失败了两轮。）
2. **列数由定义文件决定，不由图片决定**。行数/列数判断错 = 整张图切错。
3. **推进宽度必须扫描像素**（`最右非透明列 + 2`），否则所有字符等宽，`i` 与 `W` 同宽。
4. **`LUMINANCE` 模式**：白底灰度图按 alpha 读会渲染成实心白块（见第 3 节）。
5. **空格要单独给宽度**：图集里它是"空白格"，扫描只能得到约 1 像素。
6. **透明像素应为 `(0,0,0,0)`**，否则宽度扫描会出错（参考 MCPE-17913）。
7. **不要强制整数倍缩放**：那会让字号滑块看起来是坏的。
8. **图宽除不尽列数时必须拒绝**，不能凑合 —— 格子跨在字形之间，
   表现是每个字都被切错还互相粘连，而看不出是切分问题。

### 11.2 缩放与位置

9. **缩放基准是墨迹高度，不是声明的 `height`**（见 6.3）。
   按声明高度缩放会让不同图集大小不一。
10. **垂直位置没有"正确值"**：`verticalNudge` 是观感校准，
    真正的解法是给用户可调的文字偏移（见 6.4）。
11. **偏移必须在同一个 `KeyLabel` 层上统一生效**，
    否则阴影三遍里必有一遍没跟上（硬阴影曾"恰好"跟着走，柔光完全没跟）。
12. **每个键各自偏移的键是 `slotId`**，不是下标 ——
    布局调整（加 Shift、切 CPS 模式）后下标会错位，用户的调整会串到别的键上。

### 11.3 渲染

13. **染色必须用 `Modulate`**，不能用 `ColorFilter.tint(color)` 的默认 `SrcIn`
    （只看 alpha、忽略 RGB，会毁掉渐变）；**抠洞层反过来必须用 `SrcIn`**（见 6.6）。
14. **柔光要用真模糊**，多层副本在"抠洞 + 像素字形"的前提下上限不高（见 6.5）。
15. **`Modifier.blur` 要 `BlurredEdgeTreatment.Unbounded`**，
    默认会裁在组件边界内、看起来像"没生效"。
16. **注意 dp / 像素单位**：`Modifier.blur` 与 `TextStyle.Shadow.blurRadius` 吃 **dp**，
    而 `BitmapFontText` 的参数是**像素**。混错过一次（柔光半径小了 2~3 倍）。
17. **`KeyLabelText` 那类组件**要显式把柔光半径传给图片字体 ——
    它读不到 `TextStyle.Shadow`。

### 11.4 数据与字段

18. **`BitmapFontStore` 的 id 有两种形态**：存储是**裸 uuid**，对外是 `bitmap:<uuid>`。
    混用会让 `rename`/`delete` **静默失效**，也会让渲染判定"这不是图片字体"而回退矢量字体 ——
    两个看起来毫不相关的症状，同一个根因。
19. **字体类新字段沿用 `xxxFontId` 命名**，才会被 `ParamsTree` 自动处理（见 9.3）。
20. **新字段要无条件写进 JSON**，否则可能不在 `KNOWN_KEYS` 里而被报成"未识别字段"（见 9.5）。
21. **对照 `ComponentStyle` 的全部字段核对该搬的都搬了** ——
    转换器漏过 `bitmapFontId`，表现是"转换后图片字体丢了"。
22. **`TextUnit.Unspecified.value` 是 `Float.NaN`，不是 0**。
    取字距必须走 `safeLetterSpacing()` —— 漏进去会让 `penX` 变 NaN、
    **后面所有字形叠在同一位置**。症状极隐蔽：单字符正常，多字符才炸
    （看起来像"字距算错"，完全想不到是 NaN 传播）。

### 11.5 Kotlin / 构建

23. **块注释是可嵌套的**：注释里写 `image/*` 这类"斜杠 + 星号"会被当成嵌套注释开始，
    而闭合只有一层 → 整段注释永不闭合 → 后面代码全被吞掉，
    报出来的却是"某个不相关的函数未解析 / Unclosed comment"。**极难定位。**
24. **公开函数不能暴露更窄可见性的类型**（private / internal）。
    违反时声明会被判为无效，于是**引用它的地方报的是语法错误**，看起来像文件被写坏了。
25. **不要用 PowerShell 的 `Set-Content` / `Get-Content` 改 Kotlin 源码** ——
    默认编码会把中文写成乱码，而乱码在控制台上还看不出来（显示假象）。
    用 `edit` / `write` 工具。
