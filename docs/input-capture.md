# 输入读取层（root / Shizuku）

这份文档是**输入读取**子系统的设计依据：怎么读到按键、为什么这么做、
哪里不能改。改动这块之前先读这里。

> Shizuku 通道本身的选型与授权流程见 [`shizuku.md`](shizuku.md) ——
> 那份讲"借谁的权限"，这份讲"拿到权限之后怎么读事件"。

---

## 1. 一句话说清

```
主应用 ──▶ root:  su -c "/system/bin/getevent -t"
       ──▶ Shizuku: sh -c "/system/bin/getevent -t"
                  │
                  ▼  进程 stdout 的文本行
            解析成 InputEvent（type / code / value / device）
                  │
                  ▼
        CaptureController 归约成"哪些键按着"
```

两条通道**跑的是同一个命令**，差别只在"谁去起进程"。

---

## 2. ⚠️ 命令里**只用 `-t`**，绝对不要加 `-l`

这是整个子系统最大的一个坑，**踩过一次**。

| 标志 | 作用 |
|---|---|
| `-t` | 事件行加**内核时间戳**前缀 `[  12345.678901]` |
| `-l` | 把事件行从**十六进制**换成**符号名** |

```
只用 -t：  [  12345.678901] /dev/input/event3: 0001 0011 00000001
用了 -l：  [  12345.678901] /dev/input/event3: EV_KEY KEY_W DOWN
```

### 为什么加 `-l` 的症状极具迷惑性

`-l` **只影响事件行**，设备公告（`add device` / `name:`）不受影响。于是：

| | 结果 |
|---|---|
| 热插拔 | **正常**（公告照样解析） |
| 设备数显示 | **正常**（照样更新） |
| 按键 | **一个都读不到** |

一半对一半错。排查时很容易去查采集之外的地方（悬浮窗？配置？按键映射？），
而真正的原因只是命令行多了一个字母。

`GeteventParserTest` 里有一条测试**断言符号名格式解析不了**，作用就是
"谁把 `-l` 加回去，先看到测试失败，再读到这段解释"。

### ⚠️ 为什么不需要 `-l` 也能知道事件来自哪个设备

设备路径来自事件行本身的**前缀**，而那与 `-l` 无关：

```c
/* getevent.c 里那行 */
if (nfds > 1) printf("%s: ", device_names[i]);
```

条件是"**打开了多个设备**"，而全局监听必然满足。

## 3. ⚠️ 全局监听（不带 device 参数）= 热插拔

```
getevent -t              ← 不带 device 参数：监听全部设备
getevent -t /dev/input/event3   ← 带上就是单设备模式，没有热插拔
```

`getevent` 在不带 device 参数时会**自己枚举全部设备**，并在热插拔时打印：

```
add device 5: /dev/input/event3
  name:     "Xbox Wireless Controller"
remove device 5: /dev/input/event3
```

### ⚠️ 历史：这里走过一段弯路

最早是"一个设备一个 `getevent` 进程"：

```
getevent /dev/input/event0
getevent /dev/input/event2
…（启动前先 `ls /dev/input/event*` 扫一遍）
```

当时的结论写在注释里：

> `getevent /dev/input/event0 /dev/input/event1 … /dev/input/event6`
> 在真实设备上直接失败 —— 它打印用法：
> `Usage: getevent … [device]` ← **单数！**

**这个观察是对的，但推论错了**：`[device]` 是单数没错，不传 device 参数
不是"参数不足"，而是"**监听全部**"。

代价是那个方案**没有热插拔**：设备清单在启动那一刻定死，插上手柄不会开始工作，
用户得去点"重启监听"—— 而他不会知道要这么做，只会觉得"手柄没反应"。

---

## 3.1 ⚠️ 不再让用户**选设备**

这是与旧项目最大的一处产品决定，也是"全局监听"能成立的前提。

旧版要用户手动勾选 `event*` 节点。问题在于：

- **设备号会随机变**：插拔顺序、重启、换 ROM 都会让同一个设备落到别的节点上；
- **选错的表现是"按键没反应"**：用户不会想到是设备选错了，
  而排查要从"你到底勾了哪个节点"开始 —— 成本极高。

现在的做法是**全部监听**：判断"某个事件该不该点亮某个键"交给按键映射
（键码匹配）去决定 —— **设备来源不重要**。

代价是要打开更多节点，但全局监听下那本来就是一个进程的事，
换来的是"**插上就能用**"。

**所以 `InputSource.start()` 没有 `devicePaths` 参数**（见第 8 节）——
那个参数在全局模式下没有任何意义。

## 4. ⚠️ 解析：用"有没有时间戳"判定事件行

`-t` 输出里除了事件行，还有**设备描述块**：

```
add device 5: /dev/input/event3
  name:     "Xbox Wireless Controller"
  events:   KEY (0001): 0001 0002 0003 …
  input props:  00000000 00000000
```

### ⚠️ `events:` 那一行**末尾恰好是一串十六进制**

宽松的"取最后三个字段"策略会把它解析成一个**假的输入事件** ——
采集里凭空多出几个按下的键，而用户完全不知道为什么。

所以判据不能是"字段数够不够"，必须是**这一行有没有时间戳前缀**：
只有真正的事件行才有 `[ 12345.678901]`。

### ⚠️ 时间戳的数字不能参与字段解析

`12345` 与 `678901` **都是合法十六进制**。不先剥掉时间戳的话，
会解析出 `type = 0x12345`、`code = 0x678901` 这种**看起来正常但全错**的结果 ——
症状是"按键全乱、鼠标往奇怪方向动"。

### ⚠️ 旧格式的兜底判据：行首缩进 + 冒号后不是十六进制

不带 `-t` 的旧格式（单设备模式）没有时间戳，靠两条排除描述块：

| 判据 | 说明 |
|---|---|
| **行首有缩进** | 描述块一定缩进；事件行与公告行都不缩进 |
| **冒号后第一个词不是十六进制** | 覆盖 `name:` / `events:` |

⚠️ 单看第二条**不够**：`input props:  00000000` 后面那串**也是**十六进制，
所以"缩进"那条不能省。

⚠️ 也**不能用**"冒号后跟空白"当判据 —— 事件行的 `/dev/input/event3: 0001`
也是冒号后跟空白，那样会把**所有带设备前缀的事件行**都丢掉。（踩过。）

---

## 5. ⚠️ 字段解析：负数按 int 读

`getevent` 把 `struct input_event` 的字段按 **int** 打印，
所以鼠标往左/往上移动显示成 `ffffffff`。

`"ffffffff".toInt(16)` 会抛 `NumberFormatException` ——
**鼠标往左/往上移动的事件被整条丢掉**，表现为"鼠标只能往右下动"，
很容易被误判成硬件问题。

正确做法：按 `Long` 读（容忍 8 位十六进制），再截成 32 位有符号。

---

## 6. ⚠️ 设备拔出：必须释放它留下的按键

### 问题

物理设备可能在**按键还按着**的时候被拔掉 —— 那种情况内核
**不会**补发 UP 事件。不处理的话那个键会**永久卡在按下态**：
悬浮窗上一直亮着，用户完全不知道为什么，只能去重启监听。

### ⚠️ 但不能"清空全部按键"

键盘上按着 `W`、这时拔掉鼠标 —— 清空全部会把 `W` 也灭掉，
而它明明还按着。用户看到的是"**动了动鼠标，键盘上按着的键突然灭了**"。

### 做法

`HeldKeyTracker` 记"每个键由哪些设备持有"（设备 → 引用计数），
只释放"走掉那个设备独有的"。

⚠️ 用计数而不是布尔集合：同一个键可能**同时**来自多个输入节点
（一个手柄既暴露标准 evdev 节点、又暴露厂商扩展节点是常见的），
只有**所有**持有者都走了才该释放。

### ⚠️ 信号传递：`EV_DEVICE_GONE`

读取源**不自己算该释放哪些键**，而是发一个 `EV_DEVICE_GONE` 事件
（带上设备路径），由 `CaptureController` 统一处理。

这样设计有两个理由：

1. **记账只能在一个地方**：`CaptureController` 是"事件 → 按键状态"的
   唯一归约点，两条读取路径都在那里汇合。放进读取源就要各写一份，
   而两份迟早不一致。
2. **Shizuku 那条路能白拿这个能力**：它只要也发同样的信号，
   不需要再实现一遍释放逻辑。

⚠️ `EV_DEVICE_GONE` 取 `0x7F` —— 一个内核不会用到的类型值
（内核的 `EV_*` 目前到 `0x1f`），绝不会与真实事件混淆。

⚠️ 设备路径为空串时（某些 ROM 的公告只打节点序号）**释放全部键**。
保守但安全：漏清会永久卡键，误清只是"松手了"，用户再按一下就回来。

## 7. 设备数由输入源自己上报

界面上要显示"正在监听 N 个设备"，而**全局监听下这个数字由 `getevent`
的公告驱动**，还会随热插拔变化。

⚠️ 所以不能用"启动前扫一遍得到的数字"—— 那个数字**立刻就过时了**，
用户会看到"插了手柄但界面还写着 3 个设备"。

`InputSource.deviceCount` 是一个**可空的 `StateFlow`**（默认 null = 不支持），
`CaptureController` 订阅它并写进 `CaptureSession`。

⚠️ 用"可空 + 可选实现"而不是要求所有源都实现：后面的手柄 / 触屏通道
可能压根没有"设备数"这个概念，强迫它们实现一个只返回 0 的属性是噪音。

---

## 8. ⚠️ root / Shizuku 都不再预扫设备

原来启动前要 `su -c ls /dev/input/event*`，扫不到就报失败。

现在**不需要了**，而且那个检查**是有害的**：

> "**现在没有设备**"和"**读不了设备**"是两回事。
> 用户完全可能先开监听、再插手柄 —— 而那正是热插拔要支持的场景。

现在只检查 root 可用性，设备清单交给 `getevent`。

---

## 9. ⚠️ 采集的生命周期：**应用级**，不跟着悬浮窗走

只要应用进程活着，采集就一直跑。

| 事件 | 对采集的影响 |
|---|---|
| 应用启动 | **自动开始**（`CaptureController.init` 无条件 `start()`） |
| 关掉一个悬浮窗 | 无 |
| **关掉全部悬浮窗** | **无**（只停 `OverlayService`，它只管画窗口） |
| 点桌面快捷方式 | 无（`start()` 幂等兜底） |
| 调试页「重启监听」 | 停再起（唯一的用户可控入口） |
| 应用进程结束 | 采集随之结束 |

### ⚠️ 为什么拆掉"没窗口就停采集"这个耦合

旧逻辑是"采集的开关由有没有窗口决定"，理由是"没有窗口时读按键没有意义、白耗电"。
拆掉它的实际收益：

1. **不漏按键**：旧逻辑下"开悬浮窗"与"起采集"同时发生，
   那一瞬间的按键会丢。现在采集早就在跑。
2. **顺序自由**：用户可以"先插设备、再开窗口"，也可以是反过来。
   旧逻辑下前者会让人疑惑"设备怎么没反应"。
3. **少一个状态**：`prefs.captureEnabled`（"用户上次想不想开"）随之删掉了 ——
   采集不再是一个用户开关的东西，而是应用运行的一部分。

代价要说清：**一直占着一条特权通道**（root 的 `su` 子进程或 Shizuku 的远端进程）。
这是刻意的取舍，不是疏忽。空闲时几乎不耗电（没有事件就没有回调）。

### ⚠️ 但"重启监听"按钮要留着

它现在是**唯一的恢复入口**：采集连续失败后停在 `FAILED`，
而失败不再跨进程自动重试（那个机制依赖 `captureEnabled`，已经删了）。

⚠️ `CaptureController.start()` 只认 `_enabled` 这个**意图**标志，
不认"实际在不在读"。所以"采集进程被杀"之后直接调 `start()` 是**没用的**
（短路返回）。需要恢复的地方要先看 `isRunning()`：

```kotlin
if (!CaptureController.isRunning()) {
    CaptureController.stop()   // 清掉那个过期的意图标志
}
CaptureController.start()
```

见 `OverlayController.enableConfigs` —— 那段注释说明了为什么留着这一手。

## 10. 与 Axon-Input 的关系

设计参考了 [keepBacon/Axon-Input](https://github.com/keepBacon/Axon-Input)
的 `MouseInputMonitor`（全局 `getevent` + 解析设备公告），但**做了实质性调整**：

| 维度 | Axon | 本项目 |
|---|---|---|
| 命令 | `getevent -lt` | **`getevent -t`** |
| 事件行解析 | 兼容**符号名**（先找 `REL_X` 文本，再退回十六进制） | **只认十六进制** |
| 按键状态 | **按设备聚合**（`deviceButtonMasks`）再取并集 | 全局一个并集（沿用原有） |
| 设备丢失 | 在读取源里按设备释放 | 发 `EV_DEVICE_GONE`，由 `CaptureController` 释放 |
| 设备计数 | 不显示 | **要显示**，用 `StateFlow` 上报 |
| 虚拟设备过滤 | 按名字过滤自己的 uinput 节点 | **不需要**（本项目不创建 uinput 设备） |

⚠️ 最关键的调整是**故意不支持 `-l`**。Axon 用 `-lt` 并写了一套兼容两种格式的
解析；本项目反过来砍掉 `-l`。理由是：设备前缀与 `-l` 无关（见第 2 节），
所以 `-l` 对我们**没有收益**，而"支持两种格式"恰恰是那个 bug 的温床。

**结论：Axon 是很好的参照，但不要照抄命令参数** —— 它的用户场景
（它自己创建 uinput 虚拟设备、需要按名字过滤）与本项目不同。
