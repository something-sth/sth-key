# 多模式模型（标准 / 键盘 / 手柄）方案

> 状态:**设计定稿，待实施**
>
> 用户的原话:
> > 这个模型其实有三种模式是可以切换的，我在电脑上跑了一下 exe，发现这个模型有三种模式，
> > 分别是标准（键鼠），键盘，和手柄，而软件内，导入的模型不能切换模式，这一点后续我想让你完善
> >
> > 一种方案是 live2d 库里，有多模式配置的模型，加一个展开，在里面选择具体模式；
> > 另一种方案，就是动态渲染分段按钮，直接做在配置页……这种可能比较难搞。

---

## 1. 现状

导入时按 [Model3Selection] 的规则**只选一套**:

```
A-卡提/img/keyboard/cat_model/cat.model3.json   ← 被选中（变体优先级第一）
A-卡提/img/standard/cat_model/cat.model3.json   ← 丢弃
A-卡提/img/gamepad/cat_model/cat.model3.json    ← 丢弃
```

`notes` 里会提示「这个压缩包里带 4 套模型，已导入 keyboard 那一套」——
但用户**无法改变这个选择**，而三套的键帽资源、moc 都不同
（`lefthand/` `righthand/` `face/` 各一套）。

⚠️ 另外三套的**文件其实已经被解压到磁盘上了**（`extract` 是全量解压），
只是没人给它们建页面、也没登记进模型库 —— 白占空间。

---

## 2. 两种方案对比

### 方案 A:一个变体 = 一个模型库条目（推荐）

导入时给**每套完整变体**都建一个条目:

```
模型库
├── 卡提希娅（键盘）      ← live2d.modelId 指向它
├── 卡提希娅（标准）
└── 卡提希娅（手柄）
```

| 项 | 说明 |
|---|---|
| 页面写在哪 | 写到**变体自己的目录**（`img/keyboard/`），相对路径与现在完全一样 |
| 复用 | 模型选择器、配置字段 `live2d.modelId`、导出逻辑**全都不用改** |
| 每个配置选不同模式 | ✅ **天然支持**（每个配置存自己的 `modelId`） |
| 导出体积 | ✅ 只打包**被选中**的那一个变体（`collectLive2DModel` 本来就是按选中条目取目录） |
| 风险 | 低:不动数据模型，只改导入时"登记几次" |
| 代价 | 模型库里同名条目多（用后缀区分）；三套贴图都占磁盘 |

### 方案 B:一个条目 + 模式字段

模型库一条，配置里多存一个 `live2d.variant`，页面按字段切换。

| 项 | 说明 |
|---|---|
| 数据模型 | 要动 `KeyStrokesConfig`（新字段）、codec、门控表、重置规则 |
| 页面 | 要么导入时生成"三合一"页面，要么运行时换 moc/贴图（WebView 里重载） |
| 导出 | 要能把 `variant` 一起带走，还要处理"对方库里没有这个变体" |
| 风险 | 中高;而且 `live2d` 那块的"唯一真源"原则会被打破 |
| 好处 | 库干净；切换在配置页里更直观（就是用户说的方案二：分段按钮） |

---

## 3. 结论:先做 A，B 的 UI 以后可叠加

理由:

1. **A 不改数据模型** —— 这是我们这个项目里最容易出连锁 bug 的地方
   （`appliesTo` 门控表、`resetParamsToDefault`、导出兼容性都要跟着动）。
2. **A 天然满足"每个配置可以不一样"** —— 用户的真实需求是"我玩手柄就用 gamepad 那套"，
   而那本来就该是**配置**的属性，而不是模型库的全局开关。
3. 用户说的「分段按钮」在 A 之上**随时能加**:配置页读到 `modelId` 对应的
   "同一家族的其他变体"就能渲染分段控件，点了只是换个 `modelId`。

## 4. 方案 A 的实施要点

| # | 改动 | 位置 |
|---|---|---|
| 4.1 | `chooseModel3` 改成返回**全部有效候选**（按同一套排序），而不只是最优那个 | `Model3Selection` + 测试 |
| 4.2 | 导入时为每个有效变体各生成 `index.html` + `modeldata.js`，写到**该变体自己的目录** | `Live2DModelImporter.finishImport` |
| 4.3 | 每个变体各自算**摘要**（摘要只算自己目录下的文件），各自登记 | 同上 |
| 4.4 | 显示名加变体后缀:`卡提希娅（键盘）` / `（标准）` / `（手柄）` | 同上 |
| 4.5 | 贴图降采样对**每个变体**各跑一次（现在是只跑选中的那套） | 同上 |
| 4.6 | 「同一家族」的判定:`<包名>` + 变体 —— 存进 `Live2DModelEntry` 的可选字段，供以后做分段按钮 | `Live2DModels` |
| 4.7 | 只导入**一套**的老模型不受影响（`kind` / `dir` 语义不变） | — |

⚠️ 关键约束:**变体页面必须写在变体自己的目录里**。
现在的 `writeModelData` 生成的是"相对模型目录"的路径，如果统一写到包根，
这些相对路径就要改成 `../..` 形式，`file://` 下容易出错，也没必要。

⚠️ 另一个约束:摘要必须**按变体**算。现在 `computeDigest(dir)` 扫整个包目录，
三套变体的内容会混进同一个摘要 → 三者的摘要全一样 → 后两个会被"复用已有模型"吞掉。

## 5. 以后要加「配置页分段按钮」时怎么做

在 A 之上，配置页的 Live2D 那一块:

1. 配置当前 `modelId` → 查 `Live2DModelEntry.familyId`
2. 该 family 下有几个条目 → 就渲染几个分段按钮（`标准 / 键盘 / 手柄`）
3. 点击 → 只改 `modelId`（其余字段不动，**不需要新字段、不需要迁移**）
4. family 只有一个条目时不显示按钮（绝大多数模型）

⭐ 这就是为什么先做 A:分段按钮只是 A 的一个纯 UI 附加层。

## 7. 实施记录（2026-10-31）

### 7.1 已落地

| 改动 | 位置 |
|---|---|
| `chooseAll(candidates)` —— 列出全部**有效**变体（按同一套规则排序，键盘第一） | `Model3Selection`（+2 条单测） |
| `Live2DVariant(name, pageDir)` + `Live2DModelEntry.variants/variant` | `Live2DModels` |
| `pageUrl` 按选中变体算:`<dir>/<pageDir>/index.html`（单模式仍是根目录） | `Live2DModels.importedModels()` |
| `selectVariant(id, pageDir)` 持久化当前模式 | `Live2DModels` |
| 多变体导入:每套模式各写一套页面 + 各自的贴图降采样 | `Live2DModelImporter.importVariants` |
| `repairImportedPages()` 刷新**每一套**变体的页面 | 同上 |
| 库里展开选模式（`FilterChip`），切换后立刻刷新悬浮窗 | `Live2DModelPicker` |

### 7.2 与用户要求一致的两点

| 要求 | 实现 |
|---|---|
| 库里有**多模式**的模型加一个**展开**，在里面选模式 | 条目下方「模式：键盘 ▾」，展开后是三/若干个 chip |
| **导出时整个模型全部导出**，不是只导出选中的那个模式 | 导出扫的是 `entry.dir`（包根），所以三套模式都在包里；页面文件（`index.html`/`modeldata.js`）按既有规则排除，导入时重新生成 |

### 7.3 实测样本的预期结果

`鸣潮卡提希娅最牛逼键盘猫模型` 的四个候选里:

| 候选 | 有效性 | 页面目录 |
|---|---|---|
| `A-卡提/img/cat.model3.json` | ❌ 无效（孤儿） | — |
| `A-卡提/img/keyboard/cat_model/cat.model3.json` | ✅ | `A-卡提/img/keyboard` |
| `A-卡提/img/standard/cat_model/cat.model3.json` | ✅ | `A-卡提/img/standard` |
| `A-卡提/img/gamepad/cat_model/cat.model3.json` | ✅ | `A-卡提/img/gamepad` |

→ 导入后库里**一条**记录「…（键盘 / 标准 / 手柄）」，展开可切；三套页面各自独立。

⚠️ 这个包的键帽资源是 **Mver 风格**（`bg.png` / `cat.png` / `lefthand/` / `righthand/` / `face/`），
不是我们 runtime 认的 `background.png` + `left-keys/` + `right-keys/`，
所以三套都判成 `CAT`（只显示角色 + 内置键帽），**这是既有能力边界，不是本次改动引入的**。
真要把这类包的 PNG 键帽也画出来，是另一件事（见 §8）。
