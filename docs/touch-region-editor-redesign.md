# 触摸区域编辑器改版（单容器方案）

> 状态:**设计稿，未写代码**
> 目标:把"每个触摸区域一个悬浮窗、由我们自己算屏幕坐标与旋转"换成
> "**一块铺满屏幕的 View，区域用容器内相对坐标摆放**"，并把屏幕方向记录进配置，
> 方向不符时整块不显示。
>
> 参考: Axon-Input（`D:\Project\_axon\Axon-Input-main`，**只参考做法，不改它的代码**）

---

## 1. 现在的做法与它的问题

### 现状

| 环节 | 现在怎么做的 |
|---|---|
| 区域显示 | **每个触摸区域一个独立悬浮窗**（`TouchRegionEditorService.addRegion` + `regionParams`）|
| 位置 | 每个窗口各自 `setLayout(x, y, w, h)`，坐标由我们自己算 |
| 旋转 | `measureWindowOffset` / `syncRegionGeometry` / `TouchRotation` 里做补偿 |
| 保存 | 存成归一化百分比（`TouchRegionGeometry.normalizedBounds`）|

### 用户反馈的问题

> 软件似乎不知道屏幕旋转了，触摸区域被卡在左边，过不去右边，
> 软件以为现在是竖屏，实际是横屏。

### 根本原因

1. **多个窗口 + 我们自己算坐标** = 每一块都要独立做旋转补偿；补偿一错，表现为"整块卡在某一侧"。
2. 旋转的**时序**不由我们控制（配置变更、窗口重建、分屏都会插进来），
   补偿逻辑与系统实际状态之间必然存在窗口期。
3. 只要有一处算错，用户看到的就是"区域跑到屏幕外"，且很难自证。

⚠️ 结论:**这条"自己算坐标"的路本质上易错**，继续打补丁只会越来越复杂。

---

## 2. 新方案（Axon 思路）

### 一句话

**一块铺满屏幕的 View**，里面按**容器内相对坐标**摆所有触摸区域；
保存时**记录当时的屏幕方向**；当前方向与保存时不一致 → **整块不显示**。

### 为什么这样不容易错

| 点 | 说明 |
|---|---|
| 坐标 | 不再算屏幕坐标。区域的 x/y 是**容器宽高的百分比**，容器由系统铺满，我们只做一次乘法 |
| 旋转 | 旋转后系统会重新给容器布局；我们**不补偿**，只在方向不符时**不显示** |
| 旋转"卡住" | 不会发生:方向不符 = 整块隐藏（Axon 的行为），用户看到的是"没显示"而不是"错位" |
| 多窗口/分屏 | 尺寸变化超过阈值视为"不符"，同样隐藏，不再猜 |

### 与 Axon 的差异（我们的一处改进）

Axon 是"方向不符就始终不显示"，用户只能旋转回去。
我们额外提供**收起/展开**:

- **展开** = 全屏铺开，可拖可缩（编辑态）
- **收起** = 收成一个小把手（或只留一小块），不遮挡游戏画面

这样能缓解 Axon 那个"必须分屏开软件才能配置"的痛点:
在游戏里先收起，需要时展开调一下，再收起。

### 面板入口

`Touching` 面板的入口按钮**挂在这块 View 上**（悬浮小按钮 → 面板），
功能一个不减，只是换了个位置。

## 3. 数据与状态

### `TouchSettings` 新增字段

| 字段 | 类型 | 含义 |
|---|---|---|
| `savedRotation` | `Int` | 保存时的屏幕旋转（`Surface.ROTATION_0/90/180/270`）|
| `savedWidthPx` / `savedHeightPx` | `Int` | 保存时容器尺寸（用于判断分屏/自由窗口导致的比例变化）|
| `editorCollapsed` | `Boolean` | 编辑器是否处于收起状态（持久化，下次进来保持）|

⚠️ 区域的几何**保持现状**（归一化百分比）:这部分已经是对的，
换的只是"谁来铺屏幕"，不是"怎么存"。

### 方向匹配规则（**待你拍板**）

| 规则 | 说明 | 建议 |
|---|---|---|
| A. 严格（0/90/180/270 必须完全一致） | 最简单、最不会错 | ✅ **建议用这个** |
| B. 允许 180° 视为匹配 | 布局会上下颠倒，实际上不能用 | ❌ |
| C. 不匹配时自动旋转布局 | 又回到"我们算坐标" | ❌ |

分屏/自由窗口: 尺寸变化超过 **±10%** 也视为"不符"（避免比例错位）。

⚠️ 老配置没有 `savedRotation` → 视为**任意方向可用**（兼容），
用户第一次保存时写入；此后才按新规则判断。

## 4. 交互定义

| 场景 | 行为 |
|---|---|
| 进入编辑（方向匹配） | 展开全屏容器，区域可拖、可缩放 |
| 进入编辑（方向不符） | **不显示容器**；面板/通知里提示「当前方向与保存时不同，请旋转回 <方向> 后再编辑」|
| 拖动区域 | 只在容器坐标系内改百分比，保存时**不做任何旋转换算** |
| 保存 | 同时写入**当前方向**与容器尺寸 |
| 收起 | 容器缩成把手；区域不响应触摸（不遮挡游戏）|
| 展开 | 恢复全屏可编辑 |
| 旋转发生在编辑中 | 重新读 Display；匹配则重排，不匹配则隐藏并提示 |

⚠️ 命中测试: 容器本身**不拦截**触摸（`FLAG_NOT_FOCUSABLE` 等），
只有落在区域矩形内的触摸才被消费；编辑态才允许拖拽。

| 风险 | 对策 |
|---|---|
| 全屏容器抢触摸，游戏点不动 | 容器不拦截；仅编辑态消费；收起即完全不挡 |

1. 竖屏保存 → 横屏:容器消失，提示正确；转回竖屏恢复

## 10. 「收起后小圆球会不会挡住点击？」—— 不会，关键在**窗口尺寸**

### 结论先说

**收起时把窗口本身缩到圆球大小**（例如 56dp），系统里就**没有一块铺满屏幕的透明 View**了，
自然不存在"空白处拦截点击"。

⚠️ 千万不要做成"全屏窗口 + 里面画一个小圆球" —— 那才是你说的那个坑:
全屏窗口即使 `FLAG_NOT_TOUCHABLE` 之外什么都不画，也会吃掉游戏点击。

### 两种状态下的窗口形态

| 状态 | 窗口尺寸 | 触摸属性 |
|---|---|---|
| **收起（圆球）** | 只有圆球那么大（约 56dp 见方）| **可触摸**（要能拖动它）；圆球以外没有窗口 |
| **展开（编辑）** | 铺满屏幕 | 可触摸（要拖区域）；容器本身 `FLAG_NOT_FOCUSABLE`，只在编辑态消费 |
| **不显示（方向不符）** | — | 窗口根本不创建 |

### 区域在游戏里不是窗口

⚠️ 这点很重要:**区域只是"逻辑范围"**（`TouchFrameTracker` 用它做命中测试），
它**从来不需要在游戏里显示成窗口**。所以"收起"时我们只需要:圆球 + 一个标记"编辑中"的标志，
不需要给区域建任何窗口。

### 那"编辑态"怎么和游戏共存？

编辑态本来就是"用户在调位置"，全屏可触摸是**期望行为**（否则拖不动）。
调完点"收起"→ 全屏窗口销毁，只剩圆球。

### 窗口属性（编辑态）

```
LayoutParams:
  type   = TYPE_APPLICATION_OVERLAY
  flags  = FLAG_NOT_FOCUSABLE        // 不抢焦点（不弹输入法）
  format = TRANSLUCENT
```

- **不**加 `FLAG_NOT_TOUCHABLE`（编辑态要触摸）
- **不**加 `FLAG_LAYOUT_NO_LIMITS`（避免溢出到异形区）
- 区域命中在 View 内自己做（`dispatchTouchEvent` 里判断是否落在某个区域矩形内）

## 11. 「面板位置」是什么意思

指的是:点开圆球后，`Touching` 面板**从哪儿冒出来**。

| 方案 | 表现 | 适合场景 |
|---|---|---|
| **A. 固定在右上角** | 面板永远出现在屏幕同一个位置 | 好找、位置稳定 |
| **B. 跟着圆球走** | 面板从圆球当前位置展开（像从球里"长出来"）| 手感更连贯；但圆球在右下角时面板得往左/上翻，要处理边界 |

⚠️ 我建议 **B + 边界钳制**:
- 面板从圆球位置展开（视觉上"长出来"）
- 如果右边放不下就往左翻、下面放不下就往上翻
- 这样比"永远右上角"更自然，也不会因为圆球位置而找不到面板

等你确认后，这条写进实现阶段的 P4。

## 12. 面板形态（已确认）

| 元素 | 设计 |
|---|---|
| **圆球** | 收起态的唯一窗口;**点击 = 打开 `Touching` 面板**（不只是拖）|

## 13. 通用坑（从既有文档抄过来，别重复踩）

> 以下每一条都来自 `docs/multi-overlay.md` 与踩过的实际 bug。
> **换实现也必须保留这些结论。**

### 13.1 状态栏 / 导航栏 / 刘海会影响"实际可触摸区域"

- 屏幕坐标 ≠ 可用坐标:**状态栏、导航栏、手势条、刘海/挖孔、圆角**都会吃掉一块。
- 判断"区域有没有出界"时，用**可用区域**（`WindowInsets`）而不是**屏幕尺寸**。
- ⚠️ 悬浮窗自己的 insets 与内容视图的 insets 是两套:
  `TYPE_APPLICATION_OVERLAY` 默认不吃系统栏，但 View 内部做命中测试时
  仍然要按**内容区**算，否则边缘一圈"看得见、点不到"。

### 13.2 屏幕旋转必须**立刻**更新，不能等下一次进入编辑

- 编辑器在旋转时**自己监听**（`onConfigurationChanged` + `Display.rotation`），
  拿到新方向就立即:
  - 匹配 → 重新布局容器（区域按百分比自动跟上）
  - 不匹配 → **立刻销毁窗口**（不是等用户操作）
- ⚠️ 用户反馈的"卡在左边过不去"就属于"没及时更新"。**不能靠轮询**。

### 13.3 判断"屏幕变了"用**尺寸**，不是 `orientation`

- 分屏、折叠屏、改显示尺寸都会改可用区域但**不改方向**。
- 现有 `OverlayBounds` 的做法可参考:多份"上次尺寸"（进程内 + 落盘），
  因为"用户横屏用了一阵再打开应用"时进程内那份不存在。

### 13.4 像素是"像素"，百分比才进配置

- 容器内布局用 px，**存配置一律百分比**（`0..1`）。
- 旋转后容器尺寸变了，百分比自动适配 —— 这就是本方案能"不算坐标"的根本原因。

### 13.5 窗口属性会改变系统重算 insets 的时机

- 切换 `FLAG_NOT_TOUCHABLE` 会让窗口跳一下（`docs/multi-overlay.md` §8 记过）。
- ⚠️ 所以**收起/展开不要靠切 flag 实现**，而是**销毁/重建窗口**
  （尺寸不同，本来就该是两个窗口）。这样也顺带避免"全屏透明层吃掉点击"。

### 13.6 区域只是逻辑范围

- 游戏运行时区域**不需要窗口**；它只被 `TouchFrameTracker` 用于命中测试。
- 所以"收起"时不需要给区域建任何窗口（见 §10）。

## 14. P1 实施蓝图（下一轮照着写）

### 14.1 好消息:几何换算**不用新写**

容器内摆放区域可以直接复用现成的纯函数:

```kotlin
TouchRegionGeometry.bounds(
    centerX = region.centerX,
    centerY = region.centerY,
    size    = region.size,
    screenWidth  = contentWidth,   // ⚠️ 传**内容区**宽，不是整屏宽
    screenHeight = contentHeight,  // ⚠️ 同理
    density = density,
): Bounds
```

⚠️ 关键点:**把"屏幕尺寸"参数传成容器内容区尺寸**（扣掉状态栏/导航栏/刘海后的区域），
百分比就会落在内容区里 —— 这正是 §13.1 那条坑的解法，而且 `bounds()` 里
`MIN_SIDE_DP` 的下限、"画与判定用同一个取整"的约定**全部原样保留**。

### 14.2 新增文件（P1 只加、不改）

| 文件 | 作用 |
|---|---|
| `capture/touch/TouchRegionContainerService.kt` | 单容器编辑服务（**P1 只读展示**）|
| `ui/overlay/touch/TouchRegionContainerView.kt` | 容器 View（自定义 `View`，`onDraw` 画区域框）|

### 14.3 容器 View 的绘制（P1 只读）

```
onDraw:

       val b = TouchRegionGeometry.bounds(..., contentWidth, contentHeight, density)

  3. 顶部一行提示:"P1 预览 · 只读"
```

```kotlin
WindowManager.LayoutParams(
```

## 16. Axon 触屏实现读后结论（2026-11-14）

读了 `D:\Project\_axon\Axon-Input-main` 的触屏相关代码（`TouchRegionOverlayEditorView`、
`TouchDisplayStore`、`TouchInputMonitor`、`AxonInputAccessibilityService`），
结论:**它压根不算屏幕坐标，全靠"归一化 + 旋转映射"自洽。**

### 16.1 编辑器：一块全屏 View，区域是它的子 View

```java
// TouchRegionOverlayEditorView.layoutSavedRegions()
int left = Math.round(r[0] * getWidth());
int top  = Math.round(r[1] * getHeight());
```

- 区域位置 = **归一化值 × 这里自己的宽高**
- 没有任何 `getRealMetrics` / `getLocationOnScreen` / 窗口偏移补偿
- 保存时反算:`lp.leftMargin / getWidth()`

⚠️ 也就是说:**它信任"自己的尺寸 = 触摸坐标的归一化基准"**。

### 16.2 它怎么保证"自己的尺寸 = 整屏"

```java
new WindowManager.LayoutParams(
    MATCH_PARENT, MATCH_PARENT,
    TYPE_ACCESSIBILITY_OVERLAY,
    FLAG_NOT_FOCUSABLE | FLAG_LAYOUT_IN_SCREEN
        | FLAG_LAYOUT_NO_LIMITS | FLAG_HARDWARE_ACCELERATED,
    PixelFormat.TRANSLUCENT);
params.gravity = Gravity.TOP | Gravity.START;
params.layoutInDisplayCutoutMode = LAYOUT_IN_DISPLAY_CUTOUT_MODE_SHORT_EDGES;
```

⭐ 还有一句我们**漏掉的**:

```java
view.setSystemUiVisibility(
    SYSTEM_UI_FLAG_LAYOUT_STABLE
  | SYSTEM_UI_FLAG_LAYOUT_FULLSCREEN
  | SYSTEM_UI_FLAG_LAYOUT_HIDE_NAVIGATION
  | SYSTEM_UI_FLAG_IMMERSIVE_STICKY);
```

⚠️ 这句才是让窗口真正铺到状态栏/导航栏底下的关键 —— 我们只设了 flags，
所以容器被系统抬了 141px（日志里 `originOnScreen=(0,141)`、`view=1272x2659`）。

### 16.3 存储：纯归一化 + 坐标版本号

```java
static final int COORD_FULL_DISPLAY = 2;   // 标记"这套坐标是按整块显示器归一化的"
setRegion(...)  // 存 left/top/right/bottom ∈ [0,1]，且强制最小 3% 宽高
```

### 16.4 命中判定：原生按设备轴范围归一化，再按**旋转**映射

- 原生 helper 直接把触点换算成 `0..100000`（`NATIVE_COORD_SCALE`），
  也就是**设备原始轴 → 0..1**，与屏幕像素无关；
- Service 侧每帧读一次旋转并映射:

```java
case ROTATION_90:  out.x = y;      out.y = 1f - x;  break;
case ROTATION_180: out.x = 1f - x; out.y = 1f - y;  break;
case ROTATION_270: out.x = 1f - y; out.y = x;       break;
default:           out.x = x;      out.y = y;
```

⚠️ 所以"旋转"在 Axon 里是**坐标映射问题**，不是"窗口位置问题" ——
它从不移动窗口，只旋转归一化坐标。

### 16.5 对我们方案的修正（结论）

| 我们现在 | 应该改成 |
|---|---|
| 用 `displayMetrics` 整屏尺寸算百分比 | 用**容器自己的宽高**算（与 Axon 一致）|
| 减 `getLocationOnScreen` 原点偏移 | **删掉**，不再需要 |
| 靠 flags 让窗口铺满 | 补上 `setSystemUiVisibility(LAYOUT_FULLSCREEN \| LAYOUT_HIDE_NAVIGATION \| ...)` |
| — | 旋转处理与 Axon 对齐：归一化坐标按旋转映射（我们采集侧已有 `TouchRotation`）|

⚠️ 这样改完，**设备差异不再影响编辑器**:只要容器铺满整块显示，
"编辑器里看到的框"与"游戏里命中的范围"用的是同一个归一化空间，
不存在"某台设备偏 141px"的问题。

⚠️ 唯一前提:容器必须真的铺满。若某台设备仍然内缩（厂商定制），
两者会**同时**按同一基准偏移 —— 但因为我们不再做像素补偿，
它最多表现为"整体等比缩放"，不会出现"卡在左边过不去"。
