# 多悬浮窗与窗口设置

本文是多悬浮窗功能的**设计定稿**：结论、结构改动、风险。实施前先读这里。

---

## 1. 需求（已确认）

主页去掉「显示按键悬浮窗」开关与「当前配置」，改成**所有配置的名称列表 + 每项一个开关 + 每项左侧一个编辑按钮**。

- 开任意一个开关 → 启动监听；连续开多个 → **只启动一次**（不冲突）
- **全部关闭**才停止监听
- 后台被杀重进后的恢复逻辑**保留**（原来是"开关状态回写"，现在是"哪几个开着"）
- 编辑按钮：**仅当该悬浮窗开启时可点**，否则置灰
- 编辑弹窗内容：
  1. **是否可触摸**（默认开启）。关闭 = 纯贴图：不可拖动、不拦截点击
  2. **X / Y 偏移**两个滑块，默认在中间
  3. **重置坐标与偏移**按钮
- 偏移滑块**只在"可触摸"关闭时可调**
- 手动拖动**不改变**滑块值 —— 滑块是"偏移"，不是"坐标"

## 2. 已定的决策

| 事项 | 结论 |
|---|---|
| 拖动与偏移的语义 | **最终位置 = 基础坐标 + 偏移**；拖动只改基础坐标，滑块只改偏移；重置按钮把两者都清零 |
| 新窗口默认位置 | **自动阶梯错开**（每个新窗口比上一个偏移 24dp），否则会完全盖住前一个，看起来像没生效 |
| 同时开启数量 | **不硬限**，超出建议数量（3 个）时给提示 |
| 偏移滑块范围 | **可用余量**：±(屏宽 − 窗宽) / ±(屏高 − 窗高)（见 4.1，不是半屏） |
| 屏幕尺寸变化 | **重新锚定**（按窗口中心等比换算），不是只夹边界（见 4.2） |
| 「当前配置」 | **彻底删除**（数据层也没有了）。屏幕上显示什么完全由"哪几个开关开着"决定 |
| 被杀死后重进 | 保持原行为：**清空全部开关**，由用户回来手动再开（不自动恢复） |

## 3. 结构改动

### 3.1 采集侧**几乎不用改**（这是个好设计带来的红利）

`CaptureController.start()` 本身幂等，`CaptureSession` 的状态全是 StateFlow：

- 开关的语义变成"**有任意一个窗口开着**" → `start()`；全关 → `stop()`
- **线程不是问题**：按既定做法，**一个收集者扇出给所有窗口**，
  而不是每个窗口各起一个协程订阅 —— N 个窗口也只有一条订阅。

### 3.2 服务：单窗口 → 多窗口（已实现）

| 原来 | 现在 |
|---|---|
| `params` / `overlayView` 各一份 | `Map<configId, OverlayWindow>`（窗口持有自己的 view / params / styleId / 配置状态） |
| `setupDragListener(view)` 闭包捕获全局 `params` | 每个窗口各自的拖动逻辑与边界（configId 在创建时传入） |
| `applyWindowSize(config)` | 按窗口各自重算（内部先比较，没变就不动） |
| `renderedConfigLabel()`（调试页） | `renderedWindowLabels()` 列出全部窗口 |

### 3.3 本地设置（每窗口一份）

`AppPrefs` 新增一份 JSON：`{ configId: { touchable, offsetX, offsetY, baseX, baseY } }`。

**它和配置数据分开存放，所以天然不会进配置包** —— "这些设置不能导出"自动满足，
不需要在导出逻辑里写任何排除（这也正是把它们放这里的理由）。

### 3.4 主页

- `MainViewModel.overlayEnabled: Boolean` → `Set<String>`（`overlayEnabledIds`）
- 列表项：编辑按钮 + 配置名 + 开关
- 迁移：老的单开关/单坐标归到**旧版当时生效的那份配置**上。
  ⚠️ 这需要读一次 `AppPrefs.activeConfigId` —— 它是"当前配置"这个概念
  唯一还活着的地方，而且只是个**只读一次的墓碑**：`migrateLegacy` 读完立刻删掉，
  代码里没有任何长期概念（见第 2 节决策表）。

## 4. 边界与屏幕旋转

### 4.1 偏移滑块的范围：可用余量，不是"半屏"

原设计写的是"±半屏"，**实测口径不成立**：竖屏手机宽约 1080px、窗口宽约 300~500px，
半屏（540）在基础坐标不靠左时立刻超界，会被 `clamp` 吃掉 ——
用户看到的是**滑块推到中间以后窗口不再动**。

现在用 `OverlayBounds.maxOffset(w,h,screenW,screenH) = 屏幕 − 窗口`：
每一段行程都真实有效（一端贴左/上边缘，另一端贴右/下边缘），0 在正中间。
这一点对本功能特别重要：**可触摸关掉之后窗口拖不动，滑块是唯一能挪它的手段**，
不能有任何一段是死的。

### 4.2 屏幕旋转（以及分屏 / 折叠 / 改显示尺寸）

`TYPE_APPLICATION_OVERLAY` 的窗口位置是**像素**，屏幕尺寸一变，靠边靠底的窗口就会出屏。

⚠️ **只把它们夹回屏内是不行的**：竖屏放在右下角的窗口，横屏时那个 X 已经超出屏宽，
夹一下会让它"啪"地贴边 —— 用户看到一次莫名其妙的跳位。
正确做法是**重新锚定**（`OverlayBounds.rescaleToScreen`）：

- 按**窗口中心**等比换算（中心在原屏的相对位置 = 中心在新屏的相对位置）；
- 偏移量按同一比例缩放（它是"相对基准的位移"，基准尺度变了它也得跟着变，
  否则滑块中点不再是视觉上的默认位置）；
- 换算完再 `clamp`，保证不出屏。

判断"屏幕变了"用的是**屏幕尺寸本身**，不是 `orientation`：
分屏、折叠屏、显示尺寸设置都会改变可用区域却不改变方向。

**两份"上次尺寸"**：进程内的 `lastScreenSize`（同一次运行里转屏最准）与
落盘的 `AppPrefs.overlayScreenWidth/Height`（应用没运行时屏幕变过）。
两份都要有 —— 用户横着屏幕用了一阵再打开应用，进程内那份是不存在的。

### 4.3 边界（旧项目的痛点，我们这边好办）

旧项目"底部永远有一块空白拖不到"是因为**窗口尺寸写死**（固定 420 高，实际内容更矮）。
我们按内容算尺寸（`baseHeight(config, cps)`），所以边界就是：

```
x ∈ [0, 屏宽 - 窗口宽]
y ∈ [0, 屏高 - 窗口高]
```

拖动过程中**实时夹**，不是松手才夹：手指划出屏幕再划回来时，
不夹会"欠"下一大截位移（表现为拖不动了）。

> ⚠️ 一个前提：窗口尺寸**只由配置决定**，与实时的 CPS 数值无关。
> 查过 `KeyLayout.baseHeight` —— 决定高度的只有配置本身
> （CPS 模式 2 多一行、模式 3 键更高），跟"现在有没有点击"没关系。
> 所以 `windowSizePx(config)` 不传实时 CPS；传了反而会让窗口尺寸
> 跟着每秒衰减的数字抖动。

## 5. 风险

1. **内存与耗电**：每个 Live2D 窗口都是一个 WebView（常驻 WebGL 循环）。
   同时开 3 个以上在低端机上很可能卡顿 —— 所以给提示而不是硬拦（见决策表）。
2. **窗口数量与刷新**：每个窗口的尺寸/位置变化都要 `updateViewLayout` 一次。
   `updateWindowSize` / `applyPosition` 内部都**先比较再动手**，
   所以"每次同步都无条件扫一遍全部窗口"是安全的，
   比"猜哪些改动会影响尺寸"可靠（漏猜一次就是只在特定配置下出现的裁切 bug）。
3. **触摸语义**："不可触摸"用 `FLAG_NOT_TOUCHABLE`，窗口**仍在、仍渲染**，
   只是不拦截任何点击 —— 这是"贴图"这个需求的正确实现方式，
   而不是把窗口设成不可见或降低 alpha。
   ⚠️ 关掉之后窗口**拖不动**，只能靠偏移滑块或重置按钮挪它。

## 6. 实施顺序（每一步都编译验证过）

**第 3 步必须与主页一起做**：它们通过"开着的 id 集合"耦合 ——
只改服务（主页还是老的单开关），用户开不出第二个窗口；
只改主页（服务还是单窗口），开两个开关只会出现一个窗口。

1. ~~本地设置层~~ ✅：`AppPrefs` 新增每窗口设置 + 旧设置迁移 + 开着的 id 集合
2. ~~边界与偏移的数学~~ ✅：`OverlayBounds`（夹边界、偏移上限、最终位置算法、阶梯错开、重锚定）
3. ~~服务多窗口化 + 主页列表~~ ✅：`Map<configId, OverlayWindow>`、每窗口拖动/边界、
   `FLAG_NOT_TOUCHABLE`、输入单订阅扇出、采集生命周期；主页的"每配置一个开关 + 编辑按钮"
4. ~~编辑弹窗~~ ✅：可触摸开关 + 两个偏移滑块（仅不可触摸时可调）+ 重置按钮
5. ~~屏幕尺寸变化~~ ✅：`onConfigurationChanged` + 重锚定
6. ~~删除「当前配置」概念~~ ✅：`ConfigStore` 不再有 `activeId/active()/setActive()`，
   配置列表页只做增删改（点卡片 = 编辑）

## 7. 落地记录（本轮完成）

### 7.1 三个"多窗口才会暴露"的坑（都已修）

**1. 鼠标位移的零点必须由采集层负责，不能让每个消费方自己记。**
`mouseMotion` 原本是"**自进程启动以来**的累计值"，而消费方（悬浮窗）可能是后来才
出现的 —— 直接把总量交给它，它算出来的第一帧就是那个巨大的历史位移。
先前的修法是让消费方自己记一个"基准"再相减，结果要维护
「基准 + 已转发量 + 累计总量」三个变量保持一致，任何一个漂了都表现为
**鼠标朝一个方向顶到画布边缘然后彻底不动**（用户实测到的现象）。

现在改成：`CaptureSession.openMouseMotion()` 在**被调用的那一刻**记下当前总量作为零点，
返回一条"相对这个零点"的位移流。于是：

- 消费方拿到的第一个值必然是 0（不可能再有首帧巨额位移）；
- 消费方只剩一个减法（`total - sent`），没有基准变量；
- 按键是"全量状态"，仍然共用一条订阅扇出；位移是"相对量"，
  **每个窗口各订阅各的**（`startMouseFeed`）—— 共用一条就又会串味。

> ⚠️ 位移窗口**不重置也不回收**：它的位置就是零点，零点一旦失效，
> 新窗口又会拿到历史位移。一个对象几十字节，每个窗口一个可以忽略。

**2. 每个窗口各起一条按键订阅 = N 倍唤醒。**
按键能报到很高的频率，所以按键保持**一条订阅扇出给所有窗口**。
每个窗口都必须收到**全量键码集合**，不能只推变化量 ——
窗口内的语义状态机是按全量重算的。

**3. Compose 内容读到了"最后设置的那一份配置"。**
单窗口时 `createOverlayView` 里读服务上的 `currentConfig` 字段就够了；
多窗口那样做会让 N 个窗口显示同一份配置。
现在每个窗口各持一个 `MutableState<KeyStrokesConfig>`，
ComposeView 通过一个**后填的取值函数**拿到它（视图与窗口互为前提，只能这样把环打开）。

### 7.1.1 排查"猫乱动 / 猫不动"靠这三条日志

指针问题的现象（"朝一个方向顶到边""动一下就没反应"）可能是**发出去的值不对**，
也可能是**页面自己算错了**，两者的修法完全不同。所以留了三条常驻日志：

| 日志 | 说明 |
|---|---|
| `mouseDelta #N: d=(dx,dy) 屏=W×H 归一化后≈(x,y)` | 本端**发出**了什么。前 8 条逐条记，之后每 60 条一条 |
| `健康检查（位移后）：{… target:[x,y], cursor:[x,y] …}` | 页面**认为**的指针位置（0..1）。发到第 10 条位移后 600ms 补一次 |
| `健康检查（首次/复检）：…（本端按住 N 个键，已发 mouseDelta M 条）` | M 一直不涨 = 位移没送到；涨了而 target 卡在 0/1 = 值被顶到边上 |

`target` 是"位移累加出来的目标"，`cursor` 是阻尼跟随后的实际位置。
取 `state` 的办法是在 `evaluateJavascript` 里直接读 —— 它是 runtime.js 里
IIFE 顶层的 `const`，对**同页面脚本可见**，因此**不需要改那个上游 JS 文件**
（它受许可证约束要求原样转发）。

### 7.2 采集生命周期

`syncWindows()` 末尾按"有没有窗口"决定 `CaptureController.start()` / `stop()`
（`start()` 本身幂等，"连续开多个只启动一次"就落在这里），
没有窗口时再 `stopSelf()`。

- **不能**在关掉某一个窗口时停采集：关掉一个窗口而其余还在跑，
  停采集会让剩下那些窗口按键不动。
- `OverlayService.stop(context, clearEnabledIds = true)` 会**同时清空开关集合** ——
  不清的话集合里还留着一串 id，下次开任意一个开关会把它们全部一起拉起来。

### 7.3 线程与调用路径

- 窗口的增删改、`updateViewLayout`、输入扇出**全在主线程**（Service 的
  `Dispatchers.Main.immediate` 作用域 + 系统回调）。
- 采集线程只往 `CaptureSession` 的 StateFlow 写状态，不碰窗口。
- 每个窗口各有一个 `OnTouchListener` 闭包，捕获的是**自己的** `params` 与 configId
  （configId 在创建时就传进去：登记进 `windows` 发生在 `addView` 成功之后，
  那时监听器早就装好了，靠反查只能拿到 null）。

### 7.4 本机设置的存储与导出

`OverlayLayouts` 存在 `AppPrefs`（SharedPreferences），**与配置数据分开** ——
配置包只打包配置对象，压根读不到这些字段，所以"不随配置导出"不需要写任何排除逻辑。
屏幕尺寸（`overlayScreenWidth/Height`）也在这里，同属"跟这台设备绑定"的东西。

配置被删除时走 `OverlayLayouts.pruneMissing(existingIds)`：
一次清掉失效的布局记录**与**开关集合里的死 id。
⚠️ 不清死 id 的话，"全关才停监听"会被一个永远开不开的 id 永久占住。

⚠️ **启动顺序**：`SthKeyApplication` 里 `migrateLegacy`（以及 `pruneMissing`）
必须在 `CaptureController.init` **之前** —— 采集恢复读的是"哪几个窗口开着"，
而迁移正是把旧的那个布尔翻译成这份列表的地方，顺序反了老用户升级后恢复不出采集。
（`pruneMissing` 还要更晚一点：它需要配置仓库先读完才有"现存的 id 集合"。）

### 7.5 验证清单（真机）

1. 主页应看到**每个配置一行**：编辑按钮 + 名称 + 开关；未开启的编辑按钮是灰的。
2. 开两个不同的开关 → 出现两个窗口（位置阶梯错开），按键盘两个都动。
3. 关掉其中一个 → 那个窗口消失，**另一个仍在动**（采集没停）。
4. 两个都关 → 窗口全消失，主页"工作状态"回到"未监听"。
5. 编辑弹窗：关掉"可触摸"后滑块才可调；拖着滑块窗口跟着移动；
   手动拖窗口后滑块数值**不变**；"重置"把窗口放回默认错开位置。
6. 关掉"可触摸"后点窗口所在位置 → 点击穿透到下面的应用（贴图语义）。
7. 转屏 → 窗口按比例留在相近位置，没有跳出屏幕。
8. 划掉应用再打开 → 开关全部回到关闭（保持原行为）。
9. 调试页能列出所有正在显示的窗口；"全部关闭"能一次关掉。
10. **鼠标**：动一下鼠标 → 猫的鼠标/头跟随移动，**停下来它也应该停下来**，
    不能一直朝一个方向漂。用 `standard`（鼠标模型）最直观；
    `keyboard` 没有 `ParamMouseX/Y`，表现为**头与眼球**跟随。

### 7.6 真机反馈修掉的两个 bug
**1. 主页不能滚动 → 配置一多，下面的开关就点不到了。**
主页根容器是个**不能滚动**的 `Column`（配置只有两三份时看不出问题）。
加了 `verticalScroll`；⚠️ 必须放在 `padding(innerPadding)` **之后**，
否则滚动区域会把顶栏/底栏的位置算进去，内容被顶栏压住、滚到底还多一截空白。
（配置 Tab 本来就用 `ScrollableScreen` 的 LazyColumn，没这个问题。）

**2. 退出重进后开关没回到关闭状态。**
`syncOverlayState()` 只看了一次 `OverlayService.isRunning()`。
用户"退出后马上重进"时，**上一个进程的服务实例还在销毁过程中**，
此刻查它仍然是 `true` → 被当成"服务还活着"→ 开关不清 →
界面上一堆亮着的开关，而屏幕上什么都没有。

处置：查到"还在跑"时**等 800ms 再确认一次**（`SERVICE_SHUTDOWN_GRACE_MS`）。
真活着的服务会一直活着（也该保留开关，窗口马上会建出来）；
正在死的那一个等完就没了，于是走"清空"分支。

顺带把主页轮询里那段"发现服务没了只记一条日志"改成**直接对齐为全部关闭** ——
那个服务不会自己再起来，留着开关等于让用户手动一个个关。

### 7.6.1 "问屏幕多大"必须问显示器（这一条踩得最狠）

`OverlayBounds.screenSize()` 原来用 `context.resources.displayMetrics`。
那是**本应用窗口**的大小，不是屏幕大小；全屏时二者恰好相等，所以一直没暴露。
在 Android 11+ 的**分屏 / 小窗**下它会变成小窗尺寸，于是：

1. `onConfigurationChanged` → 误判"屏幕变了"（其实只是自己窗口变小）；
2. 按"小窗 ÷ 全屏"比例缩放所有坐标 → **悬浮窗位置跑偏**；
3. 错值被写进 `AppPrefs.overlayScreenWidth/Height` 存档；
4. 之后夹边界都拿"小窗宽"当屏幕宽 → **窗口被卡在屏幕左侧一小块**里，
   偏移滑块也只在错误范围内活动（真机反馈"调偏移会被卡住"）；
5. 小窗划掉 → 又按存档错值反向缩放一次，看起来"自己恢复了"。

现在走 `DisplayManager` → `Display.getRealMetrics()`。**同一处的入口一共有三个**
（夹边界、拖动、Live2D 鼠标位移归一化），三个都改了 ——
只改一个的话，另外两处照样用错尺寸。

### 7.6.2 `FLAG_LAYOUT_NO_LIMITS` 必须去掉

这个标志的语义是"允许窗口跑到屏幕外，系统不要管"，它把系统**自带的边界约束**关掉了，
于是边界全靠我们自己算，而我们算的是整块显示器高度、比窗口真实可用区域大一点。两个后果：

1. **底部能多拖一点**（系统不夹了，只有我们那个偏大的边界在夹）；
2. **开关「可触摸」时窗口跳一下**：切换 `FLAG_NOT_TOUCHABLE` 会让系统重算窗口 insets
   并重新落位，叠加在原本就偏的位置上就表现为跳。

去掉之后越界由系统兜住（它永远比我们算得准），我们算的边界退回本职：
给偏移滑块定范围、给重置定默认位置。

配套加了 `syncPositionFromActual()`：布局完成后把**系统实际给的位置**写回存档 ——
否则存档里留的是"我们请求的值"，下次任何一次重算都会把它重新应用一遍，
又变成一次跳位。

> ⚠️ 这个函数后来还改过一次：写回时**必须减掉偏移**，否则会引入一个新的漂移 bug。
> 见 7.7 第 4 条 —— 那是本轮最难查的一个问题。

### 7.6.3 只有"系统重新布局"才允许动坐标

`refreshScreenSize()` 原来每次同步都跑，而 `onStartCommand` 也会触发同步 ——
**点一次「可触摸」开关、拖一下偏移滑块都会走 onStartCommand**，
于是每一次操作都在拿尺寸做比对；当时显示器报出的尺寸只要与上次不同
（多窗口 / 分屏下很常见），就会顺势把窗口位置缩放一遍，
表现是"点一下开关，窗口往左偏一下"。

现在的规则：

- 只有 `onConfigurationChanged`（转屏 / 分屏 / 折叠）才把 `displayRelayout` 置位；
- 只有置位时才比对屏幕尺寸，而且**只在方向真的翻转**（竖↔横）时缩放坐标；
- 其余情况（包括例行 `onStartCommand`）一律不碰坐标，仅按最新配置重排窗口。

> 教训：**"位置"这种东西只该由用户的直接操作或系统明确的布局事件来改**。
> 任何"顺手重算一下"的分支都会变成偶发的跳位，而且极难复现。

### 7.6.4 旧项目为什么"不越界"：因为它什么都没做

对照 `guoqudebanben` 的 `OverlayService`：它的 `params` 只有
`FLAG_NOT_FOCUSABLE`（**没有** `FLAG_LAYOUT_NO_LIMITS`），
拖动监听里也**没有任何夹边界代码**，坐标直接写进 `params` —— 全靠系统兜住。

我们多做的那些（`FLAG_LAYOUT_NO_LIMITS` + 自己算边界）反而在和系统打架：
标志把系统约束关掉了，只剩我们那个偏大的边界。

### 7.6.5 边界数据诊断

调试页 →「悬浮窗」→「悬浮窗边界数据 → 复制」，一次给出三份尺寸：

| 项 | 含义 |
|---|---|
| 显示器 | 我们算边界用的尺寸（`getRealMetrics`） |
| 系统最大窗口区域 | `getMaximumWindowMetrics()` 报的值 |
| 每个窗口 实际 / 请求 | `params.x/y`（系统夹过）vs `base+offset`（我们请求的） |

"实际"与"请求"长期不一致，就说明系统在替我们夹 —— 这时该调的是我们的边界口径。

### 7.7 这一轮最值钱的五条经验

按"踩得最狠"排序。每一条后面都注明了对应的代码位置，改动这一块之前请先读一遍。

---

**1. 「屏幕多大」与「应用窗口多大」是两个东西 —— 混用一次就毁掉整个功能。**

`resources.displayMetrics` 给的是**本应用窗口**的尺寸。全屏时它恰好等于屏幕尺寸，
所以写错了也看不出来；一旦用户分屏 / 开小窗，它立刻变成小窗尺寸，
于是"屏幕变了"、"坐标越界"、"卡在一小块里"全都会同时出现。

规矩：**问屏幕就用显示器**（`DisplayManager` → `Display.getRealMetrics`，
封装在 `OverlayBounds.screenSize`）。同一处的入口必须**全部**改掉 ——
当时夹边界、拖动、Live2D 鼠标归一化三处各写了一遍，只改一处等于没改。

> 判据：跑一次调试页的「悬浮窗边界数据」，看"显示器"与"系统最大窗口区域"是否一致。

---

**2. 改别人的东西之前，先去翻上一版是怎么做的。**

旧项目（`guoqudebanben`）的悬浮窗**从来不越界**，而它的做法是"**什么都不做**"：
`params` 只有 `FLAG_NOT_FOCUSABLE`，拖动也**没有一行夹边界代码**，全靠系统兜住。

我们反而多加了 `FLAG_LAYOUT_NO_LIMITS`（把系统约束**关掉**）再自己算边界，
等于拆掉保护再装一个不如它的 —— 两个"边界不对"的 bug 都出在这里。

规矩：**能交给系统的就交给系统**。系统对 insets / 多窗口 / 旋转的处理永远比手算准。
我们要算的只是"给滑块定范围、给重置定默认位置"。

---

**3. 位置数据只该由「用户的直接操作」或「系统明确的布局事件」来改。**

`refreshScreenSize()` 原本每次同步都跑，而 `onStartCommand` 也会触发同步 ——
**点一次开关、拖一下滑块都会走一遍**。于是每次操作都在拿尺寸做比对，
当时尺寸只要与上次不同就会顺势缩放一遍坐标，表现是"点一下，窗口挪一下"。

规矩：用 `displayRelayout` 这样的来源标记，**只有 `onConfigurationChanged` 才允许动坐标**；
任何"顺手重算一下"的分支最后都会变成偶发跳位，而且极难复现。

---

**4. 「最终位置 = base + 偏移」这个式子，写回时必须减掉偏移。**

两个地方都错过，而且是同一个错：

| 位置 | 错误 | 后果 |
|---|---|---|
| `syncPositionFromActual` | 把**实际位置**写进 `baseX` | 每同步一次就多叠一份偏移 → **每开关一次「可触摸」就往左移一点** |
| 拖动 `ACTION_UP` | 把 `params`（最终位置）写进 `baseX` | 拖完跳一下，且每拖一次多叠一份 |

规矩：**只要往 `baseX/baseY` 写值，先减掉 offset**。
偏移是负的时候（贴屏幕右侧）它表现为"往左漂"，正的时候表现为"往右漂"，
方向随偏移符号变，所以光看现象很难联想到偏移 —— 这是它难查的原因。

顺带一个推论：任何"把实际值同步回存档"的代码都要先想清楚**存档里存的是哪个量**。

---

**5. 诊断要一次给出足够的数字，不要靠猜。**

最后能定位，靠的是调试页那个「悬浮窗边界数据」按钮一次打出三份尺寸：

```
显示器（我们算边界用的）: 2800×1272
系统最大窗口区域: 2800×1272 @(0,0)
  xxx(b920fbe8): 实际=(1742,905) 请求=(1742+-59,905+0) 尺寸=304×367
                  ↑ 系统落位      ↑ base+offset
```

`实际 ≠ 请求` 且差值**正好等于偏移** —— 这一行就把第 4 条钉死了。
没有它，我们只能继续猜"是系统夹了还是我们算错了"。

规矩：**涉及"两个量应该相等"的地方，就把两个量都打出来**。
`syncPositionFromActual`、`OverlayBounds.screenSize` 里那两条日志都是这个用意。

---

### 7.8 已知未做 / 后续

- **偏移滑块不显示绝对坐标**（它显示的是偏移像素值），这是刻意的：
  见决策表里的"拖动与偏移的语义"。
- 拖动排序仍然没做（接口 `ConfigStore.move` 在，但内置 Default 已被钉在第一位）。
- `SwitchItem` 之类旧的单开关组件仍在被调试页/设置页使用，没有清理。
- **没有自动恢复开关**：进程被回收后回到全部关闭，由用户手动再开（第 2 节决策）。
- 想知道某个入口改了什么，**先看这一节和 7.7**，那边五条经验都是真机上踩出来的。
