# 配置数据的存储形态

这一层（`domain/config`）只描述配置的**参数模型**。本文件记录已经定下来的
存储与打包约定，避免后续实现时再走一遍弯路。

> ⚠️ 这份文档早先写于"还没开始实现"的阶段，里面有几条**已被实现推翻**的设想
> （manifest 装参数、`preview.png`、`assets/images/`）。现在按实际实现重写，
> 并在末尾保留了"当初怎么想的、后来为什么改"。

## 结论

配置**不是**"一个 config.json"，而是 **zip 压缩包**，后缀 `.sthkey`。

## 为什么是 zip 而不是 json

因为样式会带上**资源文件**：

- 字体（导入的字体只存在于导出方的设备上）；
- Live2D 模型（模型目录里有 `.model3.json`、`.moc3`、贴图、动作、表情，通常几 MB）。

这些资源必须和参数一起被打包、复制、分享，所以容器只能是压缩包。
JSON 只能装参数，资源还得另想办法，最后一定会变成两套东西。

## 包内结构（**实际实现**）

```
我的配置.sthkey                （本质是 zip）
├── manifest.json              元信息：格式标识、版本、名称、描述、类型、携带的资源清单
├── params.json                全部功能参数（就是配置页能改的那些）
└── assets/
    ├── fonts/                 这份配置用到的**导入字体**（按需复制）
    │   ├── 我的字体.ttf
    │   └── 另一个字体.ttf
    └── live2d/                Live2D 模型目录（样式资源，仅 Live2D 样式携带）
        └── 模型名/…
```

### manifest 与 params 分开（这里与最初设想不同）

最初想的是"manifest.json 装参数"，实现时改成了**两个文件**：

- `manifest.json`：给人看、给列表用的轻量元信息（名称、描述、样式 id、
  以及"包里带了哪些资源"的清单）；
- `params.json`：完整的参数集合。

分开之后，未来做"配置分享预览"只需要读 manifest，不必解析全部参数；
参数结构大改时 manifest 的结构也能保持稳定。

代价是两个文件可能出现"只有一半能读"的中间态（例如解压中断），
因此导入时 **manifest 读不出来就直接报错**，不做半份入库。

### 名称与描述的唯一出处是 manifest

`params.json` 里**故意不写** `name` / `description`（见
`ConfigPackageCodec.MANIFEST_OWNED_KEYS`）。两处都写就是两个真源。
因此字段差异比较时要把它们排除，否则每导入一个自家导出的包，
报告都会说"名称、描述用了默认值"，把正常情况说成异常。

## 资源怎么进包：三种来源、只有一种要带

字体有三种来源（`FontRegistry.FontKind`），但**需要跟着包走的只有一种**：

| 来源 | 进包？ | 为什么 |
|---|---|---|
| 系统字体 `system:*` | ❌ | 每台设备都有 |
| 内置字体 `builtin:*` | ❌ | **随应用打包**，装了本应用就有一份 |
| 导入字体 `imported:*` | ✅ | 只存在于导出方的设备上 |

内置字体（Minecraft AE）当年是跟着包一起导出的，那是**多此一举** ——
它随应用打包，从"加入自定义字体"那个版本起人人都有。
现在与系统字体同一套处理：**只存 id**。一份包因此能小好几 MB。

Live2D 模型同理：`builtin:*` 的内置模型不进包，只有 `imported:*` 才进。

### 引用改写：`sthkey-font://` / `sthkey-live2d://`

进包的资源，在 `params.json` 里不能写 `imported:<本机 uuid>` ——
导入方没有那个 id。统一改写成"包内引用"：

```
params.json:  "fontId": "sthkey-font://assets/fonts/我的字体.ttf"
manifest:     登记 path / displayName / sha256
导入时:       按 sha256 查本地是否已有 → 复用；否则落盘入库 → 改写成本机 id
```

## ⚠️ 字体 id 在 params 里**不止一处**（一个真实修掉的缺口）

```
params.json
├── fontId                       ← Key 样式用（顶层）
└── custom
    └── components[]
        └── style
            └── fontId           ← **自定义 Key 里每个组件自己的字体**
```

早先导出时只改顶层那一个 `fontId`，于是自定义 Key 的组件字体
原样带着 `imported:<本机 uuid>` 出了包 —— 导入方没有这个 id，
字体**静默**回落成默认：不报错、不提示，用户只会觉得"字体好像变了"。

现在改成"扫一遍 params 树、见到字体字段就处理"（`ParamsTree`）：

- 按**键名后缀**识别（`fontId`，所以以后的 `titleFontId` 也自动覆盖），
  而不是按固定路径 —— 结构一变就不用跟着改，也就不会漏；
- 数组里的**裸字符串不动**：它们没有键名，无法判断语义，
  宁可漏掉也不要把用户写的文字内容改掉；
- 多个组件引用同一个字体时只收集一次、只落盘一次。

## 目录名：单数与复数

| 目录 | 用于 |
|---|---|
| `assets/fonts/` | **新包**（自定义 Key 可以有多个字体） |
| `assets/font/` | **只读**：老的 Key 样式包（那时一份配置只有一个字体） |

两个前缀互不误匹配（第 13 个字符是 `/` 与 `s`），所以不需要任何迁移：
读条目时各按各的前缀找。导出**一律写复数**。

## 其他约定

1. **未知字段直接忽略**，不做严格校验 —— 否则新版本导出的配置在老版本上会直接报错。
   `manifest.formatVersion` 只用于报告"包来自哪个版本"。
2. **读取时对越界值做 clamp**（百分比、半径、缩放、圆角…），
   失效的样式 id 回落到默认样式。
3. **资源路径写包内相对路径**，不写绝对路径，否则换设备立刻失效。
4. **导入的配置一律 `builtIn = false`**，否则用户会得到一个"删不掉"的配置。
5. **重名自动加序号**，导入是零操作，不会覆盖已有配置。
6. **导出后立刻回读校验**：写出去没抛异常不等于文件完整（云盘、下载管理器
   可能在流关闭后才异步落盘）。宁可当场报失败让用户重试，
   也别让他到导入时才发现是个坏包。
7. **导出失败后清理空文件并补写同名**（见下）。
8. **字体缺失不算导入失败**：那是包的问题、不是配置的问题。
   回落为默认字体，并在导入报告里**列出缺失的字体名** ——
   自定义 Key 里每个组件字体都可能不同，只说"有字体缺失"用户不知道该改哪个。

### 关于"覆盖已有文件"：SAF 做不到

用户选好目录与文件名之后，是 `ACTION_CREATE_DOCUMENT` 在**应用还没写任何
数据之前**把文件建出来的。它的语义就是"创建新文件"：遇到重名一律
**自动改名**，应用既无法请求覆盖、也拿不到"用户想覆盖"的意图
（文件管理器里那个"覆盖 / 保留两者"是它自己的 UI，不经过我们）。

改名风格还跟文件管理器有关，这一点很坑：

| 文件管理器 | 重名时的命名 |
|---|---|
| 系统默认（Files） | `布吉岛 (1).sthkey` |
| ColorOS 文件管理 | `布吉岛_1.sthkey` |

所以"目录里出现了 `xxx_1`"**不代表导出成功了**：恰恰相反，
它是**上一次导出失败留下的 0 字节空文件**占了名字，这一次才被改名。

处理办法（`ConfigPackageManager.export`）：失败 → 清掉那个空文件 →
**按同名再写一次**（名字这时正好空出来，于是最终名字不带后缀）。

⚠️ 清理的判据必须保守，因为这是全项目唯一一处删用户文件的地方。
三道保险缺一不可，且**每一条都有测试**（`test/.../ExportCleanupTest.kt`）：

1. 只删 **0 字节**的 —— 非空说明里面有东西，绝不碰；
2. 只删**名字与提交给选择器的建议名不一致**的 —— 改名是"这文件是系统
   刚替我造的"的确凿证据；名字一致说明用户选的就是它，空着也轮不到我们删；
3. **删不掉就放弃**（`ContentResolver.delete` 返回 0 时不硬来）。

## 当初的设想里被推翻的两条

- **`preview.png`（配置列表里的预览图）**：没有做。列表里的预览是**实时画**的
  （`ui/preview/ConfigPreview.kt` 直接渲染样式本身），比存一张可能过期的图更好，
  也省得包变大。
- **`assets/images/`（用于替换键帽组件的图片）**：没有做。键帽外观目前由
  `ComponentStyle` 描述（颜色 / 描边 / 圆角 / 字体），不支持贴图。
  真要做的话按 `fonts/` 这一套照搬即可：新增一个资源目录、manifest 里登记、
  `ParamsTree` 那套遍历再加一种引用前缀。

## 相关文件

| 文件 | 职责 |
|---|---|
| `data/config/ConfigPackageCodec.kt` | 包结构常量、manifest 编解码、字段差异比较 |
| `data/config/ConfigPackageManager.kt` | 导入 / 导出（zip 读写、资源落盘） |

| `test/.../data/config/ParamsTreeTest.kt` | 遍历算法的测试（含"组件字体也要改"这条） |
